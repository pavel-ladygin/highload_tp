# Высоконагруженный сервис коротких вертикальных видео

## 1. Тема, аудитория и функционал

Сервис коротких вертикальных видео для пользователей России от 12 лет. Аналог — TikTok: более 1 млрд MAU в мире на сентябрь 2021 года [1]. Расчетная аудитория в России — **56,5 млн MAU и 27,7 млн DAU** [2].

MVP включает пять функций:

1. Загрузка и публикация готового видео длительностью до 3 минут.
2. Просмотр персонализированной ленты по истории и длительности просмотров.
3. Лайки и комментарии.
4. Поиск видео по автору, тегу и названию.
5. Регистрация и авторизация пользователей.

Сервис хранит видео в трех вариантах качества: 480p, 720p и 1080p. После подтверждения лайк сразу виден пользователю, который его поставил. Публичные счетчики могут обновляться с задержкой до минуты. Ролик становится доступен после обработки и сохранения копий во всех регионах. В MVP не входят трансляции, сообщения, реклама и видеоредактор.

### 2.2. RPS

`RPS_средний = операций/сутки / 86 400`.
`RPS_пик = RPS_средний × K_пик`.
`RPS_с_запасом = RPS_пик × K_запас`, где `K_запас = 2`.

Принимаем обычный суточный пик ×2 для чтения, поиска, регистрации и авторизации, ×3 для реакций, ×4 для публикаций: в пиковый час приходится 1/12, 1/8 и 1/6 суточных операций. Запас ×2 покрывает всплеск сверх обычного пика. Это допущения; пики считаем одновременными, суточные объемы — по среднему.

«Просмотр» — один API-запрос с результатом просмотра для рекомендаций; видео передается через CDN. Поиск объединяет все три признака. Проверка сессии внутри API-запроса не считается отдельным входом.

Одна публикация создает два API-запроса и `ceil(46,44 / 4) = 12` upload-частей. На просмотр приходится `20 / 4 = 5` сегментов по 4 с. При промахе FeedCache сервис вычисляет интересы по недавней истории, запрашивает векторный поиск и списки кандидатов. Метаданные и состояния лайков читает пакетами. Повторные страницы используют готовую ленту. Перекодирование в три качества — `332 400` задач в сутки, или `3,85 / 15,39 / 30,78` задач в секунду.

### 2.3. Сеть

`Объем_сутки = операций/сутки × байт/операцию`.
`Поток_средний = объем_сутки × 8 / 86 400`; `поток_пик = поток_средний × K_пик`.

Средняя одновременная аудитория: `27,7 млн × 3 600 / 86 400 = 1 154 166,67`. Средняя выдача видео — `1 731,25 Gbit/s`, пиковая — `3 462,5 Gbit/s`. За сутки: `4 986 000 000 × 20 × 1,5 / 8 = 18 697 500 000 MB = 18 697 500 GB`. Коэффициенты пика и запаса в суточный объем не входят.

| Направление | Пик, Gbit/s | С запасом ×2, Gbit/s | Объем, GB/сутки |
| --- | ---: | ---: | ---: |
| CDN -> зрители, видео | 3 462,50 | 6 925,00 | 18 697 500 |
| Origin -> CDN, 98 % попаданий | 69,25 | 138,50 | 373 950 |
| Origin -> CDN, 90 % попаданий | 346,25 | 692,50 | 1 869 750 |
| Клиенты -> upload, оригиналы | 1,906 | 3,812 | 5 145,552 |
| Внешний API, запросы + ответы | 4,522 | 9,045 | 23 872,359 |
| Между ЦОДами: две дополнительные копии медиа | 5,427 | 10,855 | 14 653,854 |
| Между ЦОДами: две дополнительные копии продуктовых событий | 0,492 | 0,984 | 2 547,347 |

Размер API-запроса с ответом, включая HTTP-заголовки: лента и поиск — 31 KB, список комментариев — 15 KB, просмотр — 1 KB, остальные операции — 2 KB. Суточный трафик — сумма `операций × размер`, пиковый — сумма `RPS_пик × размер × 8` с коэффициентом каждого метода. Сетевые накладные расходы и повторы покрываются запасом.

Снижение byte hit ratio на один процентный пункт добавляет origin `34,625 Gbit/s` на пике. При допущении 10 % request miss: `577 083,33 × 0,1 = 57 708,33 RPS`, с запасом — `115 416,67`. Совпадение долей промахов по байтам и запросам — допущение. Эффект origin shield не учитывается.

Репликация медиа: `2 × 110 800 × (46,44 + 19,6875) MB = 14 653,854 GB/сутки`, пик ×4; оригинал копируется временно. Репликация продуктовых событий: `2 × 6 368 368 500 × 200 B = 2 547,3474 GB/сутки`; пик — сумма потоков событий с коэффициентами их действий (см. ДЗ5). Репликация реакций и метаданных учитывается отдельно от этих потоков.

## 3. Глобальная балансировка

### 3.1. Размещение и маршруты

ЦОДы размещаем в **Москве, Екатеринбурге и Новосибирске**. При отказе одного данные сохраняются в двух других. Распределение спроса **50/25/25 %** между западом России, Уралом и зоной «Сибирь и Дальний Восток» — допущение. Сравниваем с одним ЦОДом в Москве по четырем условным городам; долю восточной зоны делим поровну между Красноярском и Хабаровском:

| Точка сценария | Доля | До Москвы, км | До выбранного ЦОДа, км |
| --- | ---: | ---: | ---: |
| Нижний Новгород | 50 % | 400 | 400, Москва |
| Челябинск | 25 % | 1 490 | 190, Екатеринбург |
| Красноярск | 12,5 % | 3 350 | 640, Новосибирск |
| Хабаровск | 12,5 % | 6 140 | 3 580, Новосибирск |

Среднее расстояние с учетом долей аудитории уменьшается с **1 760 до 775 км (~56 %)**. Это расстояния по поверхности Земли, а не сетевые задержки: их нужно измерять отдельно. Видео отдается через ближайшие узлы CDN, API — через наши ЦОДы.

GeoDNS настроим на PowerDNS [8]: по одному DNS-серверу в регионе, с GeoIP и картой зон для выбора виртуального IP-адреса (VIP) API. HTTP-проверки отмечают недоступные адреса. Зоны и веса меняются оператором по задержке и загрузке и распространяются на DNS-серверы. Геолокация DNS-резолвера приблизительна.

| Домен | Назначение | Маршрут |
| --- | --- | --- |
| `api.service.example` | Лента, взаимодействия, события, управление upload | GeoDNS -> региональный API VIP |
| `upload.service.example` | Передача частей оригинала | Подписанный URL с региональным именем `upload-m/e/n.service.example` -> домашний регион автора |
| `video.service.example` | Сегменты и манифесты | CDN edge -> при miss shield -> origin выбранного здорового региона |
| `static.service.example` | Версионированная статика | CDN |

Метаданные и пользовательские записи ScyllaDB имеют три копии — по одной в каждом ЦОДе. Запись подтверждается двумя копиями (QUORUM); подтвержденные изменения переживают отказ одного ЦОДа, RPO=0 для этого сценария. Запросы к метаданным выполняются из ближайшего здорового региона и требуют межрегионального обмена. Домашний регион (home) используется для загрузки файла. Ролик публикуется только после готовности оригинала и вариантов во всех трех регионах; если один недоступен, публикация ждет [21].

```mermaid
flowchart LR
    U[Пользователь] -. DNS-запрос .-> D[PowerDNS: GeoIP + health checks]
    D -. IP выбранного региона .-> U
    U --> M[Москва: API VIP]
    U --> E[Екатеринбург: API VIP]
    U --> N[Новосибирск: API VIP]
    U --> C[Внешний CDN edge]
    C --> S[Origin shield: cache miss]
    S --> O[Здоровый origin M / E / N]
    U --> H[Upload VIP домашнего региона]
    H --> P[Обработка и сохранение 3 геокопий]
    P --> O
```

Для API и upload не используем BGP Anycast: такую схему сложнее сопровождать, а смена маршрута может оборвать активное соединение. Маршрут запросов к CDN выбирает сама CDN-платформа. Обычный DNS round-robin распределяет запросы по очереди и не учитывает ни местоположение пользователя, ни доступность приложения.

Таблица показывает средний поток и обычный суточный пик без коэффициента запаса. В ДЗ 4 мощность рассчитывается на этот пик **с запасом ×2** из ДЗ 2.2 и с аварийными долями ДЗ 3.3. Внутренние обращения ленты считаются отдельно по профилю ДЗ 5–7 и не суммируются с внешним ingress.

В обычном режиме пиковый поток API (запросы + ответы) для M/E/N составляет `2,261 / 1,131 / 1,131 Gbit/s`, upload — `0,953 / 0,477 / 0,477 Gbit/s`. Для origin при 90% попаданий CDN по объему — `173,125 / 86,563 / 86,563 Gbit/s`. CDN отдает зрителям `1 731,25 / 865,625 / 865,625 Gbit/s`; этот поток не проходит через API. Для выбора оборудования все эти пики дополнительно умножаются на 2; суточный трафик остается прежним.

API-нагрузка отказавшей Москвы делится поровну; Екатеринбурга — между Москвой и Новосибирском в пропорции 60/40; Новосибирска — между Москвой и Екатеринбургом в пропорции 40/60. Максимальные доли — **65/50/50 %**. Каждый из двух оставшихся origin должен выдерживать **50 %** общего потока при 90 % попаданий CDN. Upload остается в домашнем регионе.

TTL DNS-записи — 30 с; кэши DNS и открытые соединения могут задержать переключение. Проверки оценивают готовность API работать с кворумом ScyllaDB, а CDN отдельно исключает недоступный origin. Восстановленный регион возвращается в работу постепенно.

При отказе одного ЦОДа API переключается на здоровые регионы. Две оставшиеся копии ScyllaDB образуют кворум: чтение и запись метаданных продолжаются. Изолированный ЦОД без кворума не обслуживает авторитетные операции. Загрузка в отказавший home приостановлена, новые публикации ждут третьей копии файлов; уже опубликованные видео доступны через CDN и оставшиеся origin.

## 4. Локальная балансировка

### 4.1. Схема и резервирование

В каждом регионе работают физические Linux-серверы и пара LVS с Keepalived. Они обслуживают три VIP — для API, upload и origin. Один LVS активен, второй резервный (**2N при N = 1**); каждый рассчитан на весь входящий поток региона. IPVS выбирает пул NGINX по адресу назначения и порту. Пулы разделены, чтобы передача видео не отнимала ресурсы API.

В Direct Routing LVS меняет MAC-адрес назначения и направляет новое TCP-соединение на NGINX с наименьшим числом активных соединений (`least connections`). Метод учитывает длительность соединений, но не выравнивает точно загрузку CPU и объем трафика. LVS и NGINX должны находиться в одной L2-сети. VIP назначается loopback-интерфейсу, ARP-ответы для него подавляются. Запросы и TCP ACK проходят через LVS, ответы с VIP идут от NGINX напрямую, поэтому сетевые фильтры должны разрешать эту схему. Keepalived переносит VIP по VRRP и проверяет пул. Синхронизация IPVS может сохранить часть соединений при переключении, но не гарантирует их сохранность.

```mermaid
flowchart TB
    G[Geo DNS] --> VA[VIP API]
    H[Региональный адрес home] --> VU[VIP upload]
    C[Внешний CDN / origin shield] --> VO[VIP origin]
    VA --> L1[LVS активный]
    VU --> L1
    VO --> L1
    L2[LVS резервный: 2N] -. VRRP / IPVS sync .-> L1
    L1 --> A[NGINX API: N+1]
    L1 --> U[NGINX upload: N+1]
    L1 --> O[NGINX origin: N+1]
    A --> B[API-сервисы: внешние запросы]
    B --> I[Отдельный пул внутреннего NGINX]
    I --> B2[Целевые API-сервисы]
    FEED[Feed API] -. резервные подборки .-> I
    U --> W[Upload-сервис]
    O --> F[Object storage]
```

NGINX завершает TLS и распределяет HTTP-запросы через `least_conn` по числу активных соединений. Upstream-соединения переиспользуются. Состояние пользователя и загрузки хранится отдельно от API-сервера, поэтому sticky sessions не нужны.

Отдельный региональный пул внутреннего NGINX (§11.1) направляет gRPC-запросы к экземплярам нужного сервиса. Каждый сервис запущен как минимум в двух экземплярах на разных машинах. Точное количество определят нагрузочные испытания.

HTTP-проверки Keepalived убирают неисправный NGINX из пула LVS. Перед обновлением узел исключают из конфигурации и ждут завершения текущих запросов. После отказа одного узла остаются N серверов. Если переключился директор, клиент повторяет только безопасные запросы.

### 4.2. Производительность одного NGINX

Ориентир — тест 2019 года [5]: NGINX Ingress на Xeon Platinum 8168, 8 задействованных CPU, OpenSSL 1.1.0g. Отдельно измерены HTTPS RPS (ответ 1 KB), TLS TPS нового соединения (пустой ответ, без HT) и throughput (объекты 1 MB). Тест 2017 года [6] использует другую конфигурацию и также разделяет CPS и RPS.

| Ограничение | Ориентир [5] | 70 % для расчета |
| --- | ---: | ---: |
| HTTPS RPS | 236 703 | 165 692,1 |
| TLS CPS (SSL TPS), без HT | 31 485 | 22 039,5 |
| Поток | 8,6 Gbit/s | 6,048 Gbit/s |

На каждом узле — 8 физических ядер сопоставимой производительности, 32 GB RAM и отдельные интерфейсы 10GbE для клиентских и внутренних подключений. Предел 6,048 Gbit/s относится к каждому интерфейсу, но узким местом может стать общий канал. Память и допустимое число соединений нужно проверить испытаниями.

Запросы, TLS-соединения и сетевой поток одновременно нагружают процессор, поэтому их проверяют одним тестом с запасом 30 %. Консервативно принимаем `TLS_CPS = внешний RPS` (новое соединение на запрос); keep-alive и HTTP/2 снижают фактический CPS.

### 4.3. Число серверов

`N = ceil(max(RPS / 165 692,1; TLS_CPS / 22 039,5; Gbit/s / 6,048))`.
Здесь RPS/CPS и Gbit/s уже включают запас ×2 относительно пика ДЗ 2 и максимальные доли при отказе региона: API — 65/50/50%, origin — 50/50/50%, upload — штатные 50/25/25% без переноса из home. Запас 30% в производительности узла и дополнительный узел N+1 имеют другие назначения: ограничение загрузки и замена отказавшего узла.
В пуле устанавливаем `N+1` серверов, чтобы оставшиеся N выдерживали расчетный поток после отказа узла. Максимумы регионов относятся к разным авариям; их одновременный учет создает запас мощности.

| Пул / регион | Расчетный RPS = CPS, пик ×2 | Поток, Gbit/s, пик ×2 | N по RPS / TLS / сети | Установлено N+1 |
| --- | ---: | ---: | --- | ---: |
| API, Москва | 199 903,01 | 5,879 | 2 / 10 / 1 | 11 |
| API, Екатеринбург | 153 771,55 | 4,522 | 1 / 7 / 1 | 8 |
| API, Новосибирск | 153 771,55 | 4,522 | 1 / 7 / 1 | 8 |
| Upload, Москва | 61,56 | 1,906 | 1 / 1 / 1 | 2 |
| Upload, Екатеринбург | 30,78 | 0,953 | 1 / 1 / 1 | 2 |
| Upload, Новосибирск | 30,78 | 0,953 | 1 / 1 / 1 | 2 |
| Origin, Москва | 57 708,33 | 346,250 | 1 / 3 / 58 | 59 |
| Origin, Екатеринбург | 57 708,33 | 346,250 | 1 / 3 / 58 | 59 |
| Origin, Новосибирск | 57 708,33 | 346,250 | 1 / 3 / 58 | 59 |

Пулам NGINX требуется **72 / 69 / 69** серверов в M/E/N (**210** всего), LVS — **2 на регион** (**6** всего). DNS, приложения, хранилище, транскодирование и CDN сюда не включены. Origin ограничен сетью: `ceil(346,25 / 6,048) = 58`; после отказа одного узла остаются `58 × 6,048 = 350,784 Gbit/s`. Для API после отказа узла M дает `10 × 22 039,5 = 220 395 CPS > 199 903,02`, E/N — `7 × 22 039,5 = 154 276,5 CPS > 153 771,55`.

Входящий поток origin оценивается как 10% ответного для ACK и TLS/заголовков плюс 1 500 B на запрос: `34,625 + 57 708,33 × 1 500 × 8 / 10⁹ = 35,3175 Gbit/s`. Это обратное направление полнодуплексного канала; оно не складывается с исходящими 346,25 Gbit/s для проверки одного направления. Расчет покрывает прокси: региональные каналы и хранилище также должны выдержать этот поток плюс репликацию, repair и остальные сервисы.

### 4.4. Проверка L4 и условий отказа

У каждого LVS отдельные 100GbE front/back подключения с проектным пределом **70 Gbit/s на интерфейс и 100 млн pps**. Это требования к стенду, а не производительность, гарантируемая маркировкой сетевой карты.

Для верхней оценки M учитываем весь двунаправленный API из ДЗ 2.3, хотя ответы обходят LVS, upload и входящий origin: `5,8786 + 1,906 + 35,3175 = 43,1021 Gbit/s`. Для E/N — `4,522 + 0,953 + 35,3175 = 40,7925 Gbit/s`. Округляем до **44 Gbit/s**, ниже 70. При размере пакета 64 B верхняя оценка — `44 × 10⁹ / (64 × 8) = 85,9375 млн pps`; цель **100 млн pps** покрывает ее. Физические накладные расходы Ethernet проверяются на стенде отдельно.

CPS M: `199 903,02 + 61,56 + 57 708,33 = 257 672,91`; E/N — `153 771,55 + 30,78 + 57 708,33 = 211 510,66`. Тест пары при выключенном директоре должен подтвердить **260 тыс. новых соединений/с**, до **44 Gbit/s / 100 млн pps**, с проверкой IPVS, памяти, задержек и ошибок. Эти пределы проверяются одновременно на смешанном профиле; если цель не достигается, нужно разбить VIP между дополнительными независимыми парами или изменить конфигурацию и повторить расчет.

Схема рассчитана на отказ одного региона и одного NGINX в каждом оставшемся пуле либо на отказ одного LVS при исправной локальной сети. Два отказа в одном пуле превышают резерв N+1. Количество приложений и узлов хранения определяется отдельно, поэтому расчет балансировщиков не доказывает мощность всей системы.

### 4.5. Таймауты и повторы

Для API заданы connect timeout 0,5 с и read timeout 2 с. Чтение повторяется не более раза на другом upstream, общий лимит — 3 с. Загрузка прерывается после 60 с без прогресса; повтор части использует прежние upload ID и номер. Для origin заданы connect timeout 1 с и read inactivity 10 с; при ошибке CDN повторяет GET к другой копии. Значения уточнят по измеренным квантилям времени ответа.

Если ответ на POST лайка, комментария или завершения загрузки не пришел, клиент повторяет запрос с тем же ключом идемпотентности. Reactions API может вернуть `202`, если Kafka приняла команду и результат ещё не готов. Клиент проверяет результат по `video_id` и `operation_id` через Reactions API с ограниченной частотой. При проверке передаётся исходное действие, чтобы отличить результат от конфликта ключа.

| Video, VideoCounter | Карточка ролика и публичные счетчики просмотров, лайков и комментариев |
| SearchDocument | Копия названия, тегов и данных автора для поиска |
| UserActivity | Последние 100 просмотров и полный набор лайкнутых роликов |

| ProductEvent | События действий за 30 дней для аналитики и обучения |

| UploadSession, TranscodeTaskQueue | Прогресс загрузки, идентификатор публикации и задания по качествам |
| ProductEventBuffer, CounterBuffer | События, ожидающие доставки, и изменения счетчиков |

| IdempotencyRecord | Результат запроса для безопасного повтора |

`UserActivity` создается при первом просмотре или лайке. Бэкенд сохраняет последние 100 просмотров, вытесняя самые старые. Каждая запись содержит ID ролика, время, длительность просмотра и ролика, с бюджетом 32 B. Версия и время обновления относятся к истории. Лайки хранятся независимо от нее, вытеснение просмотра сохраняет лайк. При сборке ленты сервис читает историю и текущие лайки, вычисляет веса тегов в памяти (§7.1).

`VideoEmbedding` содержит 384 числа, описывающих название и теги ролика. Вектор вычисляется при публикации или изменении текста. Поиск по векторам выполняется при сборке ленты. Версии модели и метаданных позволяют обновлять индекс и отбрасывать запоздавшие результаты.

`CandidateEntry` — вложенная запись `CandidatePool`. Она содержит ID, теги, популярность из `VideoCounter`, длительность, время публикации и ограничения показа. Сборщик исключает удаленные и неопубликованные видео. Эти поля позволяют отбирать кандидатов до получения полных карточек.

`object_ref` в `OriginalMedia` и `VideoVariant` — ключ файла в объектном хранилище. Staging содержит части загрузки, `segment_ranges` — диапазоны сегментов готового файла. При старте загрузки сохраняются сессия и `publication_id`. Состояние обработки содержит задания и готовность копий. До `PUBLISHED` ролик скрыт от поиска и ленты (§7.2).

Для оригиналов принимаем штатное окно хранения 24 ч. Принятый файл сохраняется до готовности вариантов и геокопий, включая ожидание при отказе ЦОДа. Сырые события хранятся 30 дней. История обновляется из потока событий независимо от загрузки аналитики.

### 5.3. Консистентность и распределение нагрузки

- Логин уникален. Вход разрешен после завершения регистрации. Сессии хранятся по пользователю, отзыв проверяется при авторизации запроса.
- Подтвержденный лайк читается из актуального состояния пары `(user_id, video_id)`. Повтор команды использует прежний `operation_id` и сохраненную квитанцию. Комментарий и его исходящее событие сохраняются атомарно в одной партиции (§6.3).
- История обрабатывается по `user_id`, повторы просмотров отсекаются по `event_id`. В БД принимается более новая версия снимка. Целевая задержка истории — до 5 с. Веса интересов вычисляются при сборке ленты.
- Счетчики агрегируются по `video_id` и записываются абсолютным снимком с версией. Целевая задержка — до 25 с. Популярный ролик создает горячий ключ, поэтому события суммируются перед записью. Комментарии делятся на временные интервалы и полосы (§6.5), медиа раздает CDN.
- CandidatePool обновляется раз в 15 с. Текстовый и векторный индексы обновляются по событиям каталога с целевой задержкой до минуты. Удаления учитываются по версии, перед выдачей доступность дополнительно проверяет Video API. Кэш ленты действует до 30 минут.
- При пустой истории используются популярные и новые ролики. Отказ векторного поиска оставляет остальные генераторы. Отказ Redis включает резервную сборку (§10.3).

## 6. Физическая схема БД

### 6.1. Выбор хранилищ

ScyllaDB хранит оперативные записи по известному ключу, таблицы спроектированы под запросы. Kafka передаёт события и задания, ClickHouse хранит аналитику, OpenSearch — текстовый и векторный поиск, Ceph — файлы, Redis — кэши. Метаданные файлов хранятся в ScyllaDB. LWT — условная атомарная запись внутри одной таблицы и партиции [13]. Используется версия с поддержкой LWT и журнала изменений CDC для tablets [25].

Эти индексы восстанавливаются из `VideoById`. `CandidateEntry` — вложенная запись Redis со снимком тегов, популярности и доступности ролика.

### 6.3. Запись, повторы и производные данные

- Регистрация резервирует логин, создает PENDING-аккаунт и активирует обе записи. Каждый шаг сохраняется условно и продолжается при повторе. Хеш пароля хранится в `LoginReservation`.
- Reactions API отправляет лайки в Kafka по ключу `(user_id, video_id)`. Один обработчик LWT сохраняет состояние и квитанцию в `UserVideoState`, затем фиксирует позицию и событие транзакцией Kafka. Повтор использует квитанцию и `event_id`.
- Комментарий, результат и outbox записываются одной LWT в партиции комментариев. Подписанный `operation_id` закрепляет ID, время, интервал и полосу для повторов.
- API подтверждает просмотр после `acks=all`. Kafka Streams дедуплицирует события, обновляет историю и сохраняет состояние, снимок и позицию чтения одной транзакцией Kafka [26]. ScyllaDB принимает только снимок с более новой версией. Веса тегов вычисляются при сборке ленты.
- Обработчик счётчиков последовательно суммирует события по `video_id` и записывает абсолютные снимки с возрастающей версией.
- LWT сохраняет `PUBLISHED` и outbox-событие в `VideoById`. CDC передаёт изменения в Kafka, индексатор обновляет OpenSearch по версии карточки. Сверка описана в §10.2.

Outbox — исходящее событие рядом с изменением, которое хранится до подтверждения Kafka. Relay читает изменения CDC и доставляет события. При выходе за окно CDC повторно читает неподтвержденный outbox с QUORUM (§10.2). Потребители отсекают повторы по `event_id` [15], [19].

Обработчик каталога и счётчиков каждые 15 секунд обновляет Redis: top-100 по каждому тегу, top-500 популярных и 500 свежих роликов. После сбоя он восстанавливает состояние из каталога и доступного хвоста журнала. Удалённые и неопубликованные ролики исключаются.

### 6.4. Репликация и отказ ЦОДа

Каждая партиция ScyllaDB имеет по реплике в Москве, Екатеринбурге и Новосибирске (`M:1, E:1, N:1`). Запись и авторитетное чтение используют QUORUM, то есть две копии из трёх. LWT использует глобальный SERIAL и фиксацию QUORUM [21]. Кэш может отставать, поэтому лайки и сессии проверяются в ScyllaDB.

Проверки сессии, начатые после подтверждённого отзыва, читают актуальные данные с QUORUM. При неопределённом ответе LWT результат проверяется по ID операции.

При потере одного ЦОДа оставшиеся два продолжают работу, а изолированный ЦОД не может подтвердить запись. Подтверждённые данные переживают отказ. Межрегиональный кворум добавляет задержку и трафик.

Загрузка идёт в домашний регион. Публикация ждёт готовности вариантов во всех трёх ЦОДах. Опубликованные ролики доступны через CDN и здоровые origin.

### 6.5. Разбиение данных и расширение

ScyllaDB маршрутизирует запрос по ключу партиции через token к tablet и его репликам [14].

Комментарии разбиваются по суточным интервалам и полосам, чтобы ограничить горячие партиции. Чтение идёт по времени и курсору. Счётчики одного видео агрегируются одним последовательным обработчиком до записи снимка.

При добавлении узлов ScyllaDB переносит tablets и переключает карту размещения после догонки изменений. Новые ключи комментариев применяются со следующего интервала, старые читаются по прежней версии. Число разделов Kafka меняется с сохранением порядка ключа и позиции. Получатели игнорируют устаревшие снимки.

Снимки не дают общей атомарной точки между всеми системами, поэтому непрерывность журнала нужна для восстановления подтверждённых изменений. Время восстановления проверяется на стенде.

## 7. Алгоритмы

### 7.1. Персональная лента

**Задача.** Сформировать для пользователя упорядоченный список релевантных опубликованных видео. На входе — последние действия пользователя и каталог видео. Система подбирает кандидатов из нескольких источников и оценивает вероятность содержательного просмотра каждого ролика.

**Подготовка каталога.** При публикации видео и изменении названия или тегов модель `paraphrase-multilingual-MiniLM-L12-v2` строит нормализованный вектор из 384 чисел по названию и тегам [60]. Вход обрезается до 128 токенов модели. Версия модели и версия исходных метаданных записываются вместе с вектором. Search API хранит эмбеддинги опубликованных видео в отдельном индексе OpenSearch и ищет ближайшие векторы методом HNSW/Faiss с косинусным сходством. Начальные параметры индекса — `m=16`, `ef_construction=128`, `ef_search=100` [62]. Их качество и задержку нужно проверить на каталоге проекта. Смена версии модели требует перестроить индекс и переключить его после проверки нового выпуска.

**Сбор кандидатов.** При промахе FeedCache Feed API читает до 100 последних просмотров из UserHistory, пакетом получает метаданные этих видео через Video API и проверяет актуальные лайки через Reactions API пакетами до 20 ID. Для каждого тега вычисляется сумма вкладов просмотров:

`min(1, watched_ms / (1000 × duration_s)) × (1 + liked)`.

Просмотры с отсутствующими метаданными, неположительной длительностью ролика или отрицательным watched_ms пропускаются. В памяти запроса остаются 20 тегов с наибольшим весом. Снятый лайк влияет на следующий пересчёт согласно текущему состоянию лайка.

Feed API выбирает до трёх последних уникальных видео, просмотренных не менее чем на 10%, с доступными эмбеддингами и через Search API запрашивает до 100 соседей каждого. Чтение векторов и поиск используют один выпуск индекса. Похожие кандидаты ранжируются по максимальному сходству с выбранными видео. Из CandidatePool по кругу берутся до 300 кандидатов из списков пяти наиболее весомых тегов, 200 популярных и 200 новых. Всего получается до 1 000 кандидатов. Метаданные найденных соседей запрашиваются пакетом через Video API, у остальных кандидатов они вложены в CandidateEntry. После объединения удаляются дубликаты, просмотренные и недоступные ролики. Пустая история дает популярные и новые ролики. Пока у нового видео готовится эмбеддинг, оно участвует через свежие и теговые списки.

**Ранжирование и выдача.** L1 по кругу отбирает из непустых источников до 100 кандидатов, сохраняя порядок каждого списка. CatBoost оценивает кандидатов по сходству с историей, совпадению тегов, популярности, свежести и длительности. Цель модели — предсказать содержательный просмотр. Просмотр не менее половины ролика служит положительным примером, просмотр менее 10% — отрицательным, промежуточные случаи не входят в обучение. Признаки строятся по данным, доступным до оцениваемого просмотра. Качество проверяется на более позднем временном периоде. Итоговый порядок определяется оценкой модели, при равенстве — video_id. При ошибке модели или превышении таймаута 50 мс Feed API сохраняет порядок L1.

Итоговый список до 100 ID хранится в FeedCache 30 минут. API выдаёт по 20 видео с тем же feed_id и смещением, перед выдачей Video API проверяет доступность. После исчерпания списка или срока кэша лента собирается заново по обновлённой истории. Число кандидатов и пороги просмотра — начальные параметры. Качество отбора оценивается по Recall@100, порядок — по NDCG, производительность — по задержке и нагрузке поиска. Популярная лента дешевле, но одинаково ранжирует видео для всех пользователей. Предварительные списки соседей устаревают между пересчётами, поэтому похожие видео ищутся по текущему индексу.

**Влияние на хранение и нагрузку.** UserHistory хранит последние просмотры, UserVideoState — актуальные лайки. CandidatePool и FeedCache размещены в Redis, веса тегов вычисляются в памяти запроса. Эмбеддинги и ANN-индекс хранятся отдельно в OpenSearch. На промах FeedCache приходятся чтение истории, метаданных её видео, пакетная проверка лайков, до трёх обращений к векторному поиску, чтение CandidatePool и ранжирование до 100 кандидатов. Объёмы и частоты этих операций указаны в §5.2 и §6.

```mermaid
flowchart TB
    Catalog["Video: публикация или изменение текста"] --> Embed["Модель эмбеддингов"]
    Embed -->|"вектор + версии"| Index[("OpenSearch · ANN индекс")]
    Events["Просмотры и лайки"] --> History[("ScyllaDB · UserHistory и UserVideoState")]
    History --> Feed["Feed API · сборка при cache miss"]
    Index -->|"соседи последних просмотров"| Feed
    Pool[("Redis · CandidatePool")] --> Feed
    Feed --> L1["L1 · до 100 кандидатов"]
    L1 --> Rank["CatBoost · оценка интереса"]
    Rank --> Cache[("Redis · FeedCache")]
    L1 -->|"ошибка или таймаут модели"| Cache
    Cache --> API["Feed API · до 20 видео за запрос"]
    API --> Video["Video API · проверка и карточки"]
```

### 7.2. Возобновляемая публикация видео

**Задача.** Принять готовый ролик до трёх минут, создать варианты 480p, 720p и 1080p и включить видео в каталог после проверки копий во всех трёх регионах. До статуса PUBLISHED видео не показывается в поиске и ленте.

При открытии сессии сервис сохраняет постоянные `video_id` и `publication_id`, ключ оригинала в Ceph и состояние загрузки. Повтор запроса открытия с тем же ключом идемпотентности возвращает ту же сессию. После передачи частей Ceph собирает объект по сохранённому ключу. Если сервис упал до фиксации завершения в ScyllaDB, повтор проверяет объект по этому ключу и его checksum, затем продолжает ту же публикацию.

| Этап | Условие перехода | Действие при ошибке |
| --- | --- | --- |
| Приём | Части собраны, checksum и формат оригинала проверены | При временной ошибке повторить проверку. Некорректный файл перевести в FAILED и очистить. Просроченную незавершённую сессию закрыть и удалить её части |
| Принятие публикации | Одной условной записью в `VideoProcessingState(video_id)` сохранены ACCEPTED, манифест, три задания и их outbox-события | До сохранения не подтверждать приём. Повтор завершения использует прежние ID и не создаёт вторые логические задания |
| Транскодирование | Для каждого качества получены файл и checksum, результат зафиксирован для текущего номера попытки | Повторить только незавершённое задание. Каждая попытка пишет по отдельному неизменяемому ключу. Устаревшая попытка не может заменить принятую |
| Копирование | Проверенный вариант скопирован и сверён по checksum во всех трёх регионах | Повторить только отсутствующую или не прошедшую проверку копию. При временной недоступности региона сохранить состояние и продолжить после восстановления |
| Публикация | Готовы все девять сочетаний «качество × регион» и временные копии оригинала во всех регионах | Сначала зафиксировать READY. Затем условной записью в партиции `VideoById(video_id)` установить PUBLISHED, версию и outbox-событие каталога |

Для каждого качества создаётся одно логическое задание с постоянным ключом `(publication_id, quality)`. Повторная доставка относится к тому же заданию. Повторное выполнение после сбоя может создать новую попытку, но в состояние принимается только результат актуальной попытки.

Изменения состояния заданий и outbox сохраняются в ScyllaDB. После записи outbox relay передаёт задание в Kafka, а Worker читает оригинал из Ceph, запускает FFmpeg и сохраняет результат. Переходы между этапами подтверждаются по состоянию ScyllaDB и проверенным объектам Ceph. После окончательного сбоя ставится FAILED, фон очищает части и объекты публикации. Опоздавшие результаты попыток также удаляются. Принятый оригинал и выбранные результаты сохраняются на время ожидания региона. После успешной публикации очищаются оригинал и лишние объекты попыток.

Асинхронная обработка позволяет повторить отдельный этап и не держит клиентский запрос во время транскодирования и копирования. Публикация после готовности копий во всех регионах соответствует требованию MVP и задерживается при отказе региона. Очередь и состояние этапов размещены в `VideoProcessingState`, файлы и попытки — в Ceph, опубликованная карточка и событие каталога — в `VideoById`. Подробные потоки компонентов и обработка отказов приведены в §9.3 и §10.

## 9. Схема проекта

### 9.1. Обзор сервисов

На входе в регион LVS распределяет соединения по пулам NGINX для API, загрузки и origin. Публичные вызовы API идут по HTTPS с JSON, внутренние вызовы сервисов — по gRPC через внутренние upstream NGINX (§4.1, §8.1). Внутренний NGINX выбирает экземпляр целевого сервиса. На схемах каждый такой вызов показан одной стрелкой. Владельцы данных показаны рядом с сервисами по принципу Database per Service из лекции 9 (слайды 14, 16, 18, 20).

**Легенда.** Рамка объединяет компоненты одного сервиса. Сплошная стрелка показывает вызов, операцию с хранилищем или следующий шаг обработки. Пунктир показывает доставку событий, фоновых заданий и результатов пакетных расчётов. Если ответ API ждёт подтверждения записи в Kafka, это указано на стрелке. R — чтение, W — запись, R/W — оба действия. Стрелки к хранилищу направлены от вызывающего компонента. Фоновые компоненты помечены словом «фон». Kafka, Ceph и области данных с одинаковыми именами на разных схемах обозначают одни и те же ресурсы.

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    C["Клиент"] -->|"HTTPS / JSON"| N["LVS → NGINX API"]
    N -->|"Вход и сессии"| A["Auth API"]
    N -->|"Страница ленты"| F["Feed API"]
    N -->|"Поиск видео"| S["Search API"]
    N -->|"Карточка и загрузка"| V["Video API"]
    N -->|"Лайк или снятие"| R["Reactions API"]
    N -->|"Чтение и запись"| I["Comments API"]
    N -->|"Событие просмотра"| E["Event API"]
    F -->|"gRPC · карточки"| V
    S -->|"gRPC · карточки"| V
    C -->|"GET видео"| CDN["CDN edge / shield"]
    CDN -->|"При промахе"| O["LVS → NGINX origin"]
    O -->|"S3 R: диапазоны"| M[("Ceph · видео")]
```

**Вход и регистрация.** Auth API проверяет учётные данные и сессии. Создание и активацию аккаунта выполняет Users API.

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    A["Auth API"] -->|"gRPC · создать или активировать аккаунт"| U["Users API"]
    A -->|"R/W · логин и сессии"| AD[("ScyllaDB · Auth")]
    U -->|"R/W · данные аккаунта"| UD[("ScyllaDB · Users")]
```

Потоки действий и связи с Kafka, статистикой и DWH показаны в [§9.5](#95-действия-пользователя-счётчики-и-dwh). Для защищённых операций сервисы проверяют сессию через Auth API. Клиент получает видео через CDN по ссылке из карточки и отдельно сообщает о просмотре в Event API.

При регистрации Auth резервирует нормализованный логин, вызывает Users для создания аккаунта PENDING с тем же user_id, затем активирует резерв и аккаунт. Повтор продолжает незавершённый шаг. Вход разрешён после активации обеих записей. Auth проверяет пароль по хешу из LoginReservation и выдаёт сессию. Выпуск и отзыв сессии используют LWT, проверка читает AuthByUser с QUORUM (§6.3–6.4).

| Владелец | Область данных | Как данные доступны другим сервисам |
| --- | --- | --- |
| Авторизация | ScyllaDB: LoginReservation, AuthByUser | Auth API проверяет сессии и права |
| Пользователи | ScyllaDB: UserById | Users API управляет аккаунтом |
| Видео | ScyllaDB: VideoById, VideoProcessingState. Redis: кэш карточек. Ceph: оригиналы и варианты | Video API отдаёт карточки и статус. Каталог публикует изменения. Origin читает опубликованные медиа |
| Реакции | ScyllaDB: UserVideoState | Reactions API читает собственный лайк и результат команды. Обработчик реакций публикует события смены состояния в Kafka |
| Комментарии | ScyllaDB: CommentByVideoBucketStripe | Comments API отдаёт страницы. Изменения доставляются в Kafka через outbox и relay |
| Рекомендации | ScyllaDB — UserHistory. Redis — FeedCache, CandidatePool. Ceph — резервные подборки | Feed API вычисляет интересы, объединяет кандидатов и ранжирует их |
| Статистика | ScyllaDB: VideoCounterById | Statistics API отдаёт публичные счётчики. Снимки из Kafka обновляют CandidatePool |
| Поиск | OpenSearch — текстовый индекс и VideoEmbedding | Search API выполняет текстовые и векторные запросы, индексаторы обновляют документы по событиям каталога |
| DWH | ClickHouse: ProductEvent | Контур выгрузки DWH готовит выборки для пакетных задач |

ScyllaDB и региональный Redis физически могут обслуживать несколько сервисов. Области таблиц и ключей имеют владельца. Только компоненты владельца обращаются к своей области напрямую. Например, поиск и лента читают карточки пакетным gRPC-вызовом Video API, а сборщик CandidatePool получает изменения каталога и счётчиков из Kafka. Relay и приёмники снимков работают в контурах соответствующих владельцев.

### 9.2. Рекомендации

**Запрос ленты.** Feed API проверяет FeedCache. При промахе читает историю, пакетами получает метаданные и лайки через Video API и Reactions API, вычисляет веса тегов. Search API возвращает векторных кандидатов, Redis — общие списки. После фильтров и ранжирования итоговый порядок записывается в кэш (§7.1). Перед выдачей карточки проверяет Video API. Ошибка Redis включает резервную сборку с курсором (§10.3).

```mermaid
%%{init: {"flowchart": {"curve": "linear", "rankSpacing": 32}}}%%
flowchart LR
    A["Feed API"] -->|"R/W · FeedCache, R · CandidatePool"| R[("Redis")]
    A -->|"R · история"| H[("ScyllaDB · UserHistory")]
    A -->|"gRPC · векторы и ANN-поиск"| S["Search API"]
    S -->|"R · индекс"| O[("OpenSearch")]
    A -->|"gRPC · лайки истории"| L["Reactions API"]
    A -->|"gRPC · метаданные и проверка карточек"| V["Video API"]
    A -->|"gRPC · ранжирование"| C["CatBoost"]
    A -->|"При отказе Redis · GET подборки"| N["Внутренний NGINX"]
    N -->|"R · подборка по версии"| B[("Ceph")]
```

**Подготовка данных.** Поток просмотров обновляет историю (§9.5). Сборщик поддерживает CandidatePool в Redis и публикует региональные подборки в Ceph. По событиям каталога обработчик поиска вычисляет или обновляет эмбеддинг. Обучение CatBoost использует события из DWH.

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    K["Kafka · каталог и счетчики"] -.-> P["Сборщик CandidatePool"]
    P -->|"W · списки"| R[("Redis")]
    P -->|"W · резервные подборки"| C[("Ceph")]
    K -. "Публикация, изменение текста, удаление" .-> E["Поиск · обработчик эмбеддингов"]
    E -->|"W · вектор и версии"| O[("OpenSearch · VideoEmbedding")]
    D["DWH · события просмотра"] -.-> T["Обучение CatBoost"]
    T -. "Проверенная модель" .-> M["L2 · CatBoost"]
```

Сборщик CandidatePool применяет версии карточек и счетчиков. После потери своего состояния восстанавливается из каталога через Video API и итогов через Statistics API, затем догоняет журнал. Обработчик эмбеддингов принимает более новую версию метаданных. При смене модели строится новый индекс по снимку каталога и изменениям после него. После догонки и проверки переключается alias. Запрос фиксирует конкретный индекс для чтения векторов и поиска. Старый индекс удаляется после завершения начатых запросов. CatBoost переключается на полностью записанную и проверенную модель.

**Приём оригинала.** До выдачи адреса загрузки Video API сохраняет сессию, video_id, publication_id и ключ оригинала. Части идут в домашний регион через выделенный пул загрузки. Повтор сохраняет upload_id и номер части.

```mermaid
    subgraph VIDEO["Видео · приём"]

```

**Фоновая обработка.** Worker по заданию читает оригинал, кодирует своё качество и записывает неизменяемый объект попытки. Состояние задания определяет, какой результат принят. Проверка копий фиксирует checksum и готовность по каждому качеству и региону. Из сохранённого прогресса обработка продолжает только незаконченные шаги.

```mermaid
flowchart LR
```

### 10.1. Резервирование компонентов

Расчётный сценарий — отказ одного ЦОДа. Трафик уходит в два оставшихся (ДЗ 3.3), а пулы NGINX выдерживают потерю ещё одного узла на пул (ДЗ 4.3). Запас приложений и хранилищ проверяем на стенде.

| Компонент | Резерв и обнаружение отказа | Что происходит |
| --- | --- | --- |
| PowerDNS / GeoDNS | По серверу в каждом ЦОДе, проверки API, TTL 30 с | Неисправный VIP убирается из новых DNS-ответов. Клиенты с кэшем переключаются позже |

| ScyllaDB | По реплике в каждом ЦОДе, QUORUM 2/3. Для LWT — SERIAL + QUORUM | Два ЦОДа продолжают работу. При таймауте результат записи проверяется по ID операции |

| Relay, сверка и фоновые задачи | Резервные исполнители, сохранённые позиции или шаги. Сигналы — отставание, возраст задания и ошибки | Новый исполнитель продолжает с сохранённой позиции. Для рекомендаций сохраняется предыдущая полная версия индекса и модели |

| Upload, FFmpeg и публикация | От двух исполнителей на разных хостах. Шаги хранятся в ScyllaDB, файлы — в Ceph | Обработка продолжается с сохранённого шага. При отказе ЦОДа приём в здоровых регионах ограничен ёмкостью staging |

### 10.2. Асинхронные потоки

| Паттерн и поток | Что подтверждаем и как повторяем |
| --- | --- |
| **Очередь команд** · лайки | API ждёт `acks=all` и проверяет квитанцию в ScyllaDB. Применённая команда возвращает `200`, принятая без результата — `202`, несовпадение хеша — `409`. Обработчик одной LWT записывает состояние и квитанцию, затем транзакция Kafka фиксирует позицию и событие смены состояния. Повтор использует ту же квитанцию и `event_id` (§6.3) |
| **Transactional outbox** · комментарии, каталог и задания видео | Изменение и outbox фиксируются одной LWT в партиции. Комментарий подтверждается после LWT. Relay отмечает доставку после ack Kafka. Если отметка потерялась, повтор уйдёт с тем же `event_id`. После истечения окна CDC отдельная задача берёт неподтверждённые записи из outbox [15], [19] |
| **Сбор событий** · просмотр → Event API → Kafka | API отвечает после `acks=all`. Клиент при повторе сохраняет `event_id`. Streams отбрасывает дубли в пределах окна повтора |
| **Цепочка фоновых заданий** · загрузка → FFmpeg → геокопии → публикация | Приём оригинала подтверждаем после проверки файла и записи задания. Worker продолжает сохранённый шаг, а номер попытки защищает от опоздавшего результата. `PUBLISHED` ставится после проверки всех копий (ДЗ 7.2) |
| **Асинхронные модели чтения** · Kafka Streams → история и счётчики | Streams фиксирует позицию, состояние и выходные события одной транзакцией Kafka. Приёмник фиксирует позицию после записи более нового снимка в ScyllaDB или проверки его версии. Повтор абсолютного значения счётчика не даёт второго начисления [26] |
| **Событийное обновление поиска** · каталог → OpenSearch | Индексатор проверяет каждый ответ Bulk и сохраняет позицию, когда обновление прошло или в индексе уже есть более новая версия. Повтор версии безопасен, если она содержит то же полное состояние [41] |
| **Фоновые обновления** · CandidatePool, DWH и модели | Сборщик обновляет списки по версиям каталога и счётчиков. После сбоя начинает со снимка и догоняет журнал. Загрузчик DWH фиксирует позицию после записи пачки, выборка с `FINAL` убирает дубли по дате и ID. Новую модель CatBoost и индекс эмбеддингов включаем после подготовки и проверки (§9.2, §9.5) |

**Хранение команд лайков.** Автоудаление в отдельном топике отключаем. Удаляем только обработанный префикс до подтверждённой позиции с запасом 24 ч на технический повтор [61]. Квитанции ScyllaDB храним до очистки соответствующего участка журнала и конца клиентского окна. Лимит диска и возраст очереди контролируем до записи. При исчерпании запаса API временно отклоняет новые команды. Клиент повторяет запрос с прежним `operation_id`.

**Сверка поиска.** Фоновый процесс сравнивает версии каталога с текстовым и векторным индексами и отправляет исправления через Kafka. Для вектора также проверяет версию модели. Пустой текст исключает ролик из векторного индекса, а свежие и популярные списки сохраняют его доступность в рекомендациях. Цель — суточный обход с лимитом 5 000 карточек/с. При нагрузке на каталог или поиск сверка замедляется и продолжает с сохранённой позиции. При удалении в обоих индексах сохраняется запись `deleted=true` с версией минимум на 30 дней. Вектор из нее удаляется, запросы исключают такие документы. Позднее событие с меньшей версией отбрасывается. Старые повторы за пределами рабочего окна обрабатываются отдельно от текущих счётчиков и индекса.

### 10.3. Деградация при отказах

**1. ЦОД недоступен до READY.** Зрители смотрят опубликованные ролики через CDN и здоровые origin. Загрузка в недоступный домашний ЦОД приостанавливается. В здоровых регионах при открытии сессии резервируем место для оригинала и промежуточных файлов. При заполнении квоты API ограничивает новые загрузки. Принятые оригиналы и результаты обработки хранятся до готовности копий. Автор видит «ожидает копирования». После восстановления обработчик продолжает с сохранённого шага и дозирует копирование. `RPO 0` для медиа относится к опубликованным роликам с проверенными геокопиями. Принятый оригинал без геокопии при отказе домашнего ЦОДа ждёт восстановления площадки.

**2. Redis недоступен.** Feed API читает историю из ScyllaDB и через Search API ищет соседей до трех недавних роликов с эмбеддингами по правилам §7.1. Штатное ранжирование заменяется порядком сходства, затем добавляются общие кандидаты. При пустой истории, нехватке кандидатов или отказе векторного поиска используются популярные и новые видео региона. Сборщик CandidatePool раз в 15 с публикует полную версию общих списков в Ceph отдельной записью. Внутренний NGINX кэширует версионные подборки на диске. Подборка пригодна до 15 минут с момента публикации.

Feed API исключает дубли и просмотренные видео. Подписанный и зашифрованный курсор связывает с пользователем до 100 упорядоченных ID, позицию и срок до 15 минут, ограниченный сроком использованной подборки. На страницу Feed API передаёт одним вызовом до 40 ID в Video API и возвращает до 20 роликов после проверки публикации, удаления и прав показа. Позиция продвигается до 20-го допущенного ролика или до конца проверенного пакета, если допущенных меньше. При возврате Redis новые ленты собираются штатно, действующий резервный курсор сохраняет порядок до истечения срока. Если источники резерва недоступны, проверку нельзя выполнить или лимит параллельных вызовов исчерпан, Feed API отвечает `503`.

Пик с запасом после перераспределения нагрузки — `ceil(11 541,67 × 65%) = 7 503` пакетных вызова/с на регион, до 300 120 проверяемых ID/с. Замеряем Video API под остальным трафиком с отключённым Redis, включая промахи его кэша карточек и чтения из ScyllaDB.

### 10.4. Цели и проверка восстановления

За 30 дней цель для ленты и комментариев — 99,9% успешных ответов за 3 с. Для лайков измеряем время до приёма команды в Kafka и отдельно ставим цель 99,9% команд, применённых в ScyllaDB, за 3 с от запроса. Для ленты целевой p95 — 500 мс, отдельно измеряем долю резервных страниц и `503`. Цель публикации 99% за 10 мин действует при штатной доступности трёх ЦОДов. При отказе ЦОДа измеряем возраст очереди и время её разбора. Для счётчиков — 99% событий за 60 с.

| Отказ | Что сохраняется | Цель восстановления |
| --- | --- | --- |
| Один ЦОД | Подтверждённые записи ScyllaDB и Kafka при исправных оставшихся копиях (RPO 0) | API ≤60с для 99% контрольных запросов, Kafka/Streams ≤5 мин |
| Один LVS, NGINX или API | Подтверждённые записи хранятся вне процесса | Переключение ≤30с |
| Один ЦОД с медиа | Опубликованные ролики с проверенными геокопиями (RPO 0) | Смена origin ≤60с. Публикация ждёт восстановления копий |
| Потеря Redis | История, векторный поиск и региональные подборки доступны независимо от Redis | Лента переключается на резервный путь. Измеряем переключение и постепенный прогрев кэша |
