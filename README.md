# Высоконагруженный сервис коротких вертикальных видео

## 1. Тема, аудитория и функционал

Сервис коротких вертикальных видео для пользователей России от 12 лет. Аналог — TikTok: более 1 млрд MAU в мире на сентябрь 2021 года [1]. Расчетная аудитория в России — **56,5 млн MAU и 27,7 млн DAU** [2].

MVP включает пять функций:

1. Загрузка и публикация готового видео длительностью до 3 минут.
2. Просмотр персонализированной ленты по истории и длительности просмотров.
3. Лайки и комментарии.
4. Поиск видео по автору, тегу и названию.
5. Регистрация и авторизация пользователей.

Сервис хранит видео в трех вариантах качества: 480p, 720p и 1080p. После подтверждения лайк сразу виден пользователю, который его поставил. Публичные счетчики могут обновляться с задержкой до минуты. Ролик становится доступен после обработки и сохранения копий во всех регионах. В MVP не входят трансляции, сообщения, реклама и видеоредактор.

### 2.2. RPS

`RPS_средний = операций/сутки / 86 400`.
`RPS_пик = RPS_средний × K_пик`.
`RPS_с_запасом = RPS_пик × K_запас`, где `K_запас = 2`.

Принимаем обычный суточный пик ×2 для чтения, поиска, регистрации и авторизации, ×3 для реакций, ×4 для публикаций: в пиковый час приходится 1/12, 1/8 и 1/6 суточных операций. Запас ×2 покрывает всплеск сверх обычного пика. Это допущения; пики считаем одновременными, суточные объемы — по среднему.

«Просмотр» — один API-запрос с результатом просмотра для рекомендаций; видео передается через CDN. Поиск объединяет все три признака. Проверка сессии внутри API-запроса не считается отдельным входом.

Одна публикация создает два API-запроса и `ceil(46,44 / 4) = 12` upload-частей. На просмотр приходится `20 / 4 = 5` сегментов по 4 с. При промахе FeedCache запрос читает готовый профиль, недавнюю историю и ограниченные списки кандидатов; метаданные соседей запрашиваются пакетом. Повторные страницы используют готовую ленту. Перекодирование в три качества — `332 400` задач в сутки, или `3,85 / 15,39 / 30,78` задач в секунду.

### 2.3. Сеть

`Объем_сутки = операций/сутки × байт/операцию`.
`Поток_средний = объем_сутки × 8 / 86 400`; `поток_пик = поток_средний × K_пик`.

Средняя одновременная аудитория: `27,7 млн × 3 600 / 86 400 = 1 154 166,67`. Средняя выдача видео — `1 731,25 Gbit/s`, пиковая — `3 462,5 Gbit/s`. За сутки: `4 986 000 000 × 20 × 1,5 / 8 = 18 697 500 000 MB = 18 697 500 GB`. Коэффициенты пика и запаса в суточный объем не входят.

| Направление | Пик, Gbit/s | С запасом ×2, Gbit/s | Объем, GB/сутки |
| --- | ---: | ---: | ---: |
| CDN -> зрители, видео | 3 462,50 | 6 925,00 | 18 697 500 |
| Origin -> CDN, 98 % попаданий | 69,25 | 138,50 | 373 950 |
| Origin -> CDN, 90 % попаданий | 346,25 | 692,50 | 1 869 750 |
| Клиенты -> upload, оригиналы | 1,906 | 3,812 | 5 145,552 |
| Внешний API, запросы + ответы | 4,522 | 9,045 | 23 872,359 |
| Между ЦОДами: две дополнительные копии медиа | 5,427 | 10,855 | 14 653,854 |
| Между ЦОДами: две дополнительные копии продуктовых событий | 0,492 | 0,984 | 2 547,347 |

Размер API-запроса с ответом, включая HTTP-заголовки: лента и поиск — 31 KB, список комментариев — 15 KB, просмотр — 1 KB, остальные операции — 2 KB. Суточный трафик — сумма `операций × размер`, пиковый — сумма `RPS_пик × размер × 8` с коэффициентом каждого метода. Сетевые накладные расходы и повторы покрываются запасом.

Снижение byte hit ratio на один процентный пункт добавляет origin `34,625 Gbit/s` на пике. При допущении 10 % request miss: `577 083,33 × 0,1 = 57 708,33 RPS`, с запасом — `115 416,67`. Совпадение долей промахов по байтам и запросам — допущение. Эффект origin shield не учитывается.

Репликация медиа: `2 × 110 800 × (46,44 + 19,6875) MB = 14 653,854 GB/сутки`, пик ×4; оригинал копируется временно. Репликация продуктовых событий: `2 × 6 368 368 500 × 200 B = 2 547,3474 GB/сутки`; пик — сумма потоков событий с коэффициентами их действий (см. ДЗ5). Репликация профилей, реакций и метаданных в эти строки не включена.

## 3. Глобальная балансировка

### 3.1. Размещение и маршруты

ЦОДы размещаем в **Москве, Екатеринбурге и Новосибирске**. При отказе одного данные сохраняются в двух других. Распределение спроса **50/25/25 %** между западом России, Уралом и зоной «Сибирь и Дальний Восток» — допущение. Сравниваем с одним ЦОДом в Москве по четырем условным городам; долю восточной зоны делим поровну между Красноярском и Хабаровском:

| Точка сценария | Доля | До Москвы, км | До выбранного ЦОДа, км |
| --- | ---: | ---: | ---: |
| Нижний Новгород | 50 % | 400 | 400, Москва |
| Челябинск | 25 % | 1 490 | 190, Екатеринбург |
| Красноярск | 12,5 % | 3 350 | 640, Новосибирск |
| Хабаровск | 12,5 % | 6 140 | 3 580, Новосибирск |

Среднее расстояние с учетом долей аудитории уменьшается с **1 760 до 775 км (~56 %)**. Это расстояния по поверхности Земли, а не сетевые задержки: их нужно измерять отдельно. Видео отдается через ближайшие узлы CDN, API — через наши ЦОДы.

GeoDNS настроим на PowerDNS [8]: по одному DNS-серверу в регионе, с GeoIP и картой зон для выбора виртуального IP-адреса (VIP) API. HTTP-проверки отмечают недоступные адреса. Зоны и веса меняются оператором по задержке и загрузке и распространяются на DNS-серверы. Геолокация DNS-резолвера приблизительна.

| Домен | Назначение | Маршрут |
| --- | --- | --- |
| `api.service.example` | Лента, взаимодействия, события, управление upload | GeoDNS -> региональный API VIP |
| `upload.service.example` | Передача частей оригинала | Подписанный URL с региональным именем `upload-m/e/n.service.example` -> домашний регион автора |
| `video.service.example` | Сегменты и манифесты | CDN edge -> при miss shield -> origin выбранного здорового региона |
| `static.service.example` | Версионированная статика | CDN |

Метаданные и пользовательские записи ScyllaDB имеют три копии — по одной в каждом ЦОДе. Запись подтверждается двумя копиями (QUORUM); подтвержденные изменения переживают отказ одного ЦОДа, RPO=0 для этого сценария. Запросы к метаданным выполняются из ближайшего здорового региона и требуют межрегионального обмена. Домашний регион (home) используется для загрузки файла. Ролик публикуется только после готовности оригинала и вариантов во всех трех регионах; если один недоступен, публикация ждет [21].

```mermaid
flowchart LR
    U[Пользователь] -. DNS-запрос .-> D[PowerDNS: GeoIP + health checks]
    D -. IP выбранного региона .-> U
    U --> M[Москва: API VIP]
    U --> E[Екатеринбург: API VIP]
    U --> N[Новосибирск: API VIP]
    U --> C[Внешний CDN edge]
    C --> S[Origin shield: cache miss]
    S --> O[Здоровый origin M / E / N]
    U --> H[Upload VIP домашнего региона]
    H --> P[Обработка и сохранение 3 геокопий]
    P --> O
```

Для API и upload не используем BGP Anycast: такую схему сложнее сопровождать, а смена маршрута может оборвать активное соединение. Маршрут запросов к CDN выбирает сама CDN-платформа. Обычный DNS round-robin распределяет запросы по очереди и не учитывает ни местоположение пользователя, ни доступность приложения.

Таблица показывает средний поток и обычный суточный пик без коэффициента запаса. В ДЗ 4 мощность рассчитывается на этот пик **с запасом ×2** из ДЗ 2.2 и с аварийными долями ДЗ 3.3. Внутренние обращения ленты считаются отдельно по профилю ДЗ 5–7 и не суммируются с внешним ingress.

TTL DNS-записи — 30 с; кэши DNS и открытые соединения могут задержать переключение. Проверки оценивают готовность API работать с кворумом ScyllaDB, а CDN отдельно исключает недоступный origin. Восстановленный регион возвращается в работу постепенно.

При отказе одного ЦОДа API переключается на здоровые регионы. Две оставшиеся копии ScyllaDB образуют кворум: чтение и запись метаданных продолжаются. Изолированный ЦОД без кворума не обслуживает авторитетные операции. Загрузка в отказавший home приостановлена, новые публикации ждут третьей копии файлов; уже опубликованные видео доступны через CDN и оставшиеся origin.

## 4. Локальная балансировка

### 4.1. Схема и резервирование

В каждом регионе работают физические Linux-серверы и пара LVS с Keepalived. Они обслуживают три VIP — для API, upload и origin. Один LVS активен, второй резервный (**2N при N = 1**); каждый рассчитан на весь входящий поток региона. IPVS выбирает пул NGINX по адресу назначения и порту. Пулы разделены, чтобы передача видео не отнимала ресурсы API.

В Direct Routing LVS меняет MAC-адрес назначения и направляет новое TCP-соединение на NGINX с наименьшим числом активных соединений (`least connections`). Метод учитывает длительность соединений, но не выравнивает точно загрузку CPU и объем трафика. LVS и NGINX должны находиться в одной L2-сети. VIP назначается loopback-интерфейсу, ARP-ответы для него подавляются. Запросы и TCP ACK проходят через LVS, ответы с VIP идут от NGINX напрямую, поэтому сетевые фильтры должны разрешать эту схему. Keepalived переносит VIP по VRRP и проверяет пул. Синхронизация IPVS может сохранить часть соединений при переключении, но не гарантирует их сохранность.

```mermaid
flowchart TB
    G[Geo DNS] --> VA[VIP API]
    H[Региональный адрес home] --> VU[VIP upload]
    C[Внешний CDN / origin shield] --> VO[VIP origin]
    VA --> L1[LVS активный]
    VU --> L1
    VO --> L1
    L2[LVS резервный: 2N] -. VRRP / IPVS sync .-> L1
    L1 --> A[NGINX API: N+1]
    L1 --> U[NGINX upload: N+1]
    L1 --> O[NGINX origin: N+1]
    A --> B[API-сервисы: внешние запросы]
    B --> I[Внутренний NGINX upstream на API-серверах]
    I --> B2[Целевые API-сервисы]
    U --> W[Upload-сервис]
    O --> F[Object storage]
```

NGINX завершает TLS и распределяет HTTP-запросы через `least_conn` по числу активных соединений. Upstream-соединения переиспользуются. Состояние пользователя и загрузки хранится отдельно от API-сервера, поэтому sticky sessions не нужны.

На API-серверах внутренний NGINX направляет запросы к нужному сервису напрямую. Каждый сервис запущен как минимум в двух экземплярах на разных машинах. Точное количество определят нагрузочные испытания.

HTTP-проверки Keepalived убирают неисправный NGINX из пула LVS. Перед обновлением узел исключают из конфигурации и ждут завершения текущих запросов. После отказа одного узла остаются N серверов. Если переключился директор, клиент повторяет только безопасные запросы.

### 4.2. Производительность одного NGINX

Ориентир — тест 2019 года [5]: NGINX Ingress на Xeon Platinum 8168, 8 задействованных CPU, OpenSSL 1.1.0g. Отдельно измерены HTTPS RPS (ответ 1 KB), TLS TPS нового соединения (пустой ответ, без HT) и throughput (объекты 1 MB). Тест 2017 года [6] использует другую конфигурацию и также разделяет CPS и RPS.

| Ограничение | Ориентир [5] | 70 % для расчета |
| --- | ---: | ---: |
| HTTPS RPS | 236 703 | 165 692,1 |
| TLS CPS (SSL TPS), без HT | 31 485 | 22 039,5 |
| Поток | 8,6 Gbit/s | 6,048 Gbit/s |

На каждом узле — 8 физических ядер сопоставимой производительности, 32 GB RAM и отдельные интерфейсы 10GbE для клиентских и внутренних подключений. Предел 6,048 Gbit/s относится к каждому интерфейсу, но узким местом может стать общий канал. Память и допустимое число соединений нужно проверить испытаниями.

Запросы, TLS-соединения и сетевой поток одновременно нагружают процессор, поэтому их проверяют одним тестом с запасом 30 %. Консервативно принимаем `TLS_CPS = внешний RPS` (новое соединение на запрос); keep-alive и HTTP/2 снижают фактический CPS.

### 4.3. Число серверов

`N = ceil(max(RPS / 165 692,1; TLS_CPS / 22 039,5; Gbit/s / 6,048))`.
Здесь RPS/CPS и Gbit/s уже включают запас ×2 относительно пика ДЗ 2 и максимальные доли при отказе региона: API — 65/50/50%, origin — 50/50/50%, upload — штатные 50/25/25% без переноса из home. Запас 30% в производительности узла и дополнительный узел N+1 имеют другие назначения: ограничение загрузки и замена отказавшего узла.
В пуле устанавливаем `N+1` серверов, чтобы оставшиеся N выдерживали расчетный поток после отказа узла. Максимумы регионов относятся к разным авариям; их одновременный учет создает запас мощности.

| Пул / регион | Расчетный RPS = CPS, пик ×2 | Поток, Gbit/s, пик ×2 | N по RPS / TLS / сети | Установлено N+1 |
| --- | ---: | ---: | --- | ---: |
| API, Москва | 199 903,01 | 5,879 | 2 / 10 / 1 | 11 |
| API, Екатеринбург | 153 771,55 | 4,522 | 1 / 7 / 1 | 8 |
| API, Новосибирск | 153 771,55 | 4,522 | 1 / 7 / 1 | 8 |
| Upload, Москва | 61,56 | 1,906 | 1 / 1 / 1 | 2 |
| Upload, Екатеринбург | 30,78 | 0,953 | 1 / 1 / 1 | 2 |
| Upload, Новосибирск | 30,78 | 0,953 | 1 / 1 / 1 | 2 |
| Origin, Москва | 57 708,33 | 346,250 | 1 / 3 / 58 | 59 |
| Origin, Екатеринбург | 57 708,33 | 346,250 | 1 / 3 / 58 | 59 |
| Origin, Новосибирск | 57 708,33 | 346,250 | 1 / 3 / 58 | 59 |

Пулам NGINX требуется **72 / 69 / 69** серверов в M/E/N (**210** всего), LVS — **2 на регион** (**6** всего). DNS, приложения, хранилище, транскодирование и CDN сюда не включены. Origin ограничен сетью: `ceil(346,25 / 6,048) = 58`; после отказа одного узла остаются `58 × 6,048 = 350,784 Gbit/s`. Для API после отказа узла M дает `10 × 22 039,5 = 220 395 CPS > 199 903,02`, E/N — `7 × 22 039,5 = 154 276,5 CPS > 153 771,55`.

Входящий поток origin оценивается как 10% ответного для ACK и TLS/заголовков плюс 1 500 B на запрос: `34,625 + 57 708,33 × 1 500 × 8 / 10⁹ = 35,3175 Gbit/s`. Это обратное направление полнодуплексного канала; оно не складывается с исходящими 346,25 Gbit/s для проверки одного направления. Расчет покрывает прокси: региональные каналы и хранилище также должны выдержать этот поток плюс репликацию, repair и остальные сервисы.

### 4.4. Проверка L4 и условий отказа

У каждого LVS отдельные 100GbE front/back подключения с проектным пределом **70 Gbit/s на интерфейс и 100 млн pps**. Это требования к стенду, а не производительность, гарантируемая маркировкой сетевой карты.

Для верхней оценки M учитываем весь двунаправленный API из ДЗ 2.3, хотя ответы обходят LVS, upload и входящий origin: `5,8786 + 1,906 + 35,3175 = 43,1021 Gbit/s`. Для E/N — `4,522 + 0,953 + 35,3175 = 40,7925 Gbit/s`. Округляем до **44 Gbit/s**, ниже 70. При размере пакета 64 B верхняя оценка — `44 × 10⁹ / (64 × 8) = 85,9375 млн pps`; цель **100 млн pps** покрывает ее. Физические накладные расходы Ethernet проверяются на стенде отдельно.

CPS M: `199 903,02 + 61,56 + 57 708,33 = 257 672,91`; E/N — `153 771,55 + 30,78 + 57 708,33 = 211 510,66`. Тест пары при выключенном директоре должен подтвердить **260 тыс. новых соединений/с**, до **44 Gbit/s / 100 млн pps**, с проверкой IPVS, памяти, задержек и ошибок. Эти пределы проверяются одновременно на смешанном профиле; если цель не достигается, нужно разбить VIP между дополнительными независимыми парами или изменить конфигурацию и повторить расчет.

Схема рассчитана на отказ одного региона и одного NGINX в каждом оставшемся пуле либо на отказ одного LVS при исправной локальной сети. Два отказа в одном пуле превышают резерв N+1. Количество приложений и узлов хранения определяется отдельно, поэтому расчет балансировщиков не доказывает мощность всей системы.

### 4.5. Таймауты и повторы

Для API заданы connect timeout 0,5 с и read timeout 2 с. Чтение повторяется не более раза на другом upstream, общий лимит — 3 с. Загрузка прерывается после 60 с без прогресса; повтор части использует прежние upload ID и номер. Для origin заданы connect timeout 1 с и read inactivity 10 с; при ошибке CDN повторяет GET к другой копии. Значения уточнят по измеренным квантилям времени ответа.

Если ответ на POST лайка, комментария или завершения загрузки не пришел, клиент повторяет запрос с тем же ключом идемпотентности: приложение возвращает сохраненный результат, не создавая дубль. ID события позволяет отбросить повтор. События обрабатываются отдельно от формирования ответа ленты.

### 5.1. Назначение данных и потоков

`CandidateEntry` — вложенное значение снимка `CandidatePool`, а не самостоятельная таблица или сущность физического хранения. Связи с `Video` и `VideoCounter` обозначают логические ссылки и источники данных; физическая проверка FK здесь не задается. `video_id` копируется из `Video`, `tags` содержит его теги без повторов, `popularity` — снимок `VideoCounter.view_count`. При сборке пула пропускаются удаленные и неопубликованные ролики; копируемые в CandidateEntry поля eligibility позволяют фильтровать контент по региону, возрасту и модерации без отдельного чтения Video на каждого кандидата.

`Video` хранит название, теги и длительность; `SearchDocument` — перестраиваемую копию для поиска по ролику и автору. Обработчик просмотров обновляет историю в `UserActivity` и дельту счетчика; лайк сразу меняет полный набор лайков и асинхронно обновляет счетчик. Публичные счетчики хранятся в `VideoCounter`.

`UserActivity.recent_views` — кольцевой список до 100 просмотров, а `liked_video_ids` сохраняется полностью и независимо от лимита истории. Логическое состояние возникает при первом просмотре или лайке; отсутствие истории означает пустой список, отсутствие лайка — отсутствие ID в наборе. `head`, `version` и `updated_at` описывают только недавнюю историю; общей атомарной версии истории и всего набора лайков нет. Количество лайков отдельно не хранится. Физическое представление определено в разделе 6.

В истории хранятся до 100 просмотров: ID ролика, время обработки, длительность просмотра и ролика, отметка уже учтенного лайка. Бюджет одной записи — 32 B.

`UserInterestProfile` хранит до 20 тегов с весами интереса. Обработчик событий обновляет профиль по просмотрам и лайкам; старые интересы постепенно затухают. Запрос ленты читает готовый профиль, а не пересчитывает его из истории.

`ItemSimilarity` хранит до 100 похожих видео на ролик. Сходство рассчитывается offline по совместным просмотрам. `CandidatePool` содержит общие списки по тегам, популярности и новизне. Генераторы читают эти данные по ключам; алгоритмы и порядок выдачи описаны в ДЗ 7.1.

`ProductEvent` хранит сырые события действий MVP за 30 дней для аналитики; более старую пользовательскую статистику MVP не обещает. Обработчик истории читает поток событий независимо от загрузки в DWH; онлайн-сборка ленты не сканирует `ProductEvent` в ClickHouse и не отправляет туда запросы за историей пользователя.

Публикация — отдельное состояние `VideoProcessingState`: готовность трех качеств и их копий по регионам не выводится из наличия одного объекта. До отметки `PUBLISHED` видео не попадает в поиск и CandidatePool.

Файлы хранятся как объекты по `object_ref`; staging содержит части загрузки. После сборки объем оригинала учитывается один раз. Оригинал удаляется после готовности вариантов и их региональных копий; штатное окно — до 24 ч. `segment_ranges` описывает диапазоны внутри варианта видео.

### 5.3. Консистентность и распределение нагрузки

- Логин уникален; незавершенная регистрация не дает права входа. Регистрация имеет восстанавливаемое состояние: повтор продолжает ту же операцию, успех возвращается после готовности аккаунта и учетных данных. Одновременная атомарная запись разных сущностей не требуется. Токены хранятся в виде хеша; сессия действует до истечения срока или отзыва.
- Изменение лайка/комментария согласовано с результатом операции и исходящим событием. Ключ идемпотентности имеет область `(user_id, operation, target_ref, operation_id)`, где `target_ref` обозначает целевой объект; повтор с теми же параметрами в течение 24 ч возвращает сохраненный результат, с другим содержимым — конфликт. Повторная доставка события не создает вторую дельту в пределах поддерживаемого окна повторов.
- История и профиль интересов обновляются одним обработчиком по user_id. Повторы событий отсекаются по event_id. Состояние и позиция обработки сохраняются согласованно; в ScyllaDB передаются версионированные снимки, поэтому повтор записи не начисляет интерес заново.
- Счетчики группируются по `video_id`: один Kafka partition key направляет события видео одному последовательному обработчику. Обработчик складывает дельты и пакетно публикует абсолютный снимок с возрастающей версией; принимающая сторона применяет только версию новее сохраненной. Повтор снимка не прибавляет счетчик второй раз. События и состояние не разносятся по полосам одного видео. Чтение медиа обслуживает CDN.
- Обработчик обновляет историю и профиль интересов с целевой задержкой до 5 с; счетчики — до 25 с, CandidatePool — до 15 с; поисковый индекс может отставать до минуты. ItemSimilarity пересчитывается offline по 30-дневному окну; допустимое отставание и расписание — проектные параметры, качество требует проверки. FeedCache хранит готовый список до 30 минут. При недоступности профиля применяются общие генераторы popular/recent; при пустой истории — те же генераторы. При отставании используются последние версии профиля, индекса и списка.

## 6. Физическая схема БД

### 6.1. Выбор хранилищ

ScyllaDB хранит оперативные данные: аккаунты, лайки, историю, карточки видео и комментарии. Основные запросы обращаются по известному ключу, поэтому таблицы строятся под эти запросы. LWT — условная атомарная запись — объединяет изменения только внутри одной таблицы и партиции [13]. Используется версия с поддержкой LWT и CDC для tablets [25].

Kafka передает события и задания, ClickHouse хранит аналитику, OpenSearch обслуживает поиск, Ceph — видеофайлы, Redis — восстанавливаемый кэш. В ScyllaDB находятся метаданные файлов и ссылки на объекты.

### 6.3. Запись, повторы и производные данные

- **Регистрация:** LWT резервирует нормализованный логин, затем создается аккаунт PENDING, активируется резерв и аккаунт. Незавершенный шаг можно продолжить; вход разрешен только после завершения. Хеш пароля хранится в LoginReservation.
- **Лайк и комментарий:** состояние, результат запроса и исходящее событие сохраняются одной LWT в своей таблице и партиции. Ключ повтора — `(user_id, operation, target_ref, operation_id)`, срок — 24 ч. Другой payload с тем же ключом отклоняется. Подписанный operation_id комментария закрепляет его ID, время, интервал и полосу: повтор не меняет маршрут.
- **Просмотры:** API отправляет событие непосредственно в Kafka и подтверждает прием после `acks=all`; при повторе сохраняется event_id. Отдельная авторитетная запись просмотра в ScyllaDB до Kafka не создается; историю/интересы обновляет потребитель с дедупликацией.
- **История и профиль:** события дедуплицируются по event_id, затем обрабатываются по user_id. Kafka Streams согласованно сохраняет состояние, выходные снимки и позицию чтения. ScyllaDB принимает только более новую версию снимка; общая транзакция Kafka–ScyllaDB не требуется [26].
- **Счетчики:** ключ Kafka — video_id. Один обработчик последовательно суммирует события ролика и раз в несколько секунд записывает абсолютный итог с версией. Повторы событий отсекаются, повторная запись того же снимка итог не увеличивает. После сбоя обработчик восстанавливается из журнала. Это сокращает записи в БД; пропускную способность на самом популярном видео нужно проверить отдельно.
- **Публикация и поиск:** переход карточки в PUBLISHED и outbox-событие фиксируются одной LWT в партиции VideoById; индексатор читает Kafka и проверяет каждый результат Bulk. Фоновая сверка и версионированные tombstone описаны в [§10.2](#102-асинхронные-потоки).
- **Доставка:** CDC читает исходящие записи с QUORUM и передает их в Kafka. Возможны повторы; потребители проверяют event_id. При отставании за пределы хранения CDC отдельная задача повторно отправляет неподтвержденные исходящие записи. Единой транзакции ScyllaDB–Kafka нет [15], [19].
- **Авторизация:** сессии и auth_epoch находятся в одной пользовательской партиции. Выпуск и отзыв используют LWT; проверки, начатые после подтвержденного отзыва, читают актуальное состояние с QUORUM. При неопределенном результате LWT выполняется SERIAL-чтение и повтор по исходному ключу.

`UserInterestProfile` и `UserHistory` хранят текущие снимки, а не все версии. `ItemSimilarityByVideo` пересчитывается offline и публикуется целиком под новой index_version; после переключения запросы используют один согласованный выпуск индекса. Старый выпуск удаляется после истечения связанных кэшей.

`CandidatePool` обновляется отдельным обработчиком изменений каталога и счетчиков. Раз в 15 с он публикует в Redis top-100 по каждому тегу, общий top-500 популярных и 500 свежих роликов. Состояние каталога и теговый индекс восстанавливаются из снимка актуального каталога и доступного хвоста журнала; 24-часовой журнал не содержит весь многолетний каталог. Удаленные и неопубликованные видео в списки не включаются; запрос ленты каталог не сканирует.

### 6.4. Репликация и отказ ЦОДа

NetworkTopologyStrategy задает число копий отдельно по ЦОДам: `M: 1, E: 1, N: 1` (Москва, Екатеринбург, Новосибирск). Итого три копии каждой партиции, по одной в каждом ЦОДе. Запись и авторитетное чтение используют QUORUM — две копии из трех. LWT использует глобальный SERIAL и фиксацию QUORUM [21]. Кэш применяется для карточек с допустимым отставанием, но не заменяет проверку собственного лайка или сессии.

При отказе одного ЦОДа оставшиеся два продолжают чтение и запись. Изолированный ЦОД не может подтвердить запись в одиночку. Подтвержденные данные переживают потерю одного ЦОДа (RPO=0 для этого сценария); при таймауте исход операции проверяется по ее ID. Для отказного режима в оставшихся ЦОДах предусматривается запас ресурсов. Межрегиональный кворум добавляет задержку и служебный трафик — это цена выбранной сохранности.

Домашний регион сохраняется для загрузки файлов. Новые ролики публикуются после готовности файлов во всех трех ЦОДах; при недоступности одного публикация ждет. Уже опубликованные видео доступны через CDN и оставшиеся origin.

### 6.5. Разбиение данных и расширение

Маршрут: **ключ партиции -> token -> tablet -> узлы с копиями**. Tablets — переносимые диапазоны таблицы, а не серверы [14].

Полезный объем на копию: аккаунты — 113 GB, метаданные видео — 404 GB, история и лайки — 7,64 TB, комментарии — 46,59 TB. Для каждой таблицы отдельно учитываем ключи, версии, квитанции за 8 суток и рост, затем три копии, журналы, backup и резерв при отказе/переносе. Число диапазонов зависит от объема и нагрузки; число узлов — от емкости и производительности оборудования.

Комментарии делятся на суточные интервалы и полосы; чтение объединяет результаты по времени и курсору. Счетчики хранятся одной записью на видео и обновляются пакетно одним обработчиком. События одного видео между независимыми потоками не распределяются.

**Добавление серверов:** ScyllaDB копирует выбранные tablets, догоняет изменения и переключает карту размещения; затем освобождает старые копии. Запросы продолжаются через драйвер, хеш ID не меняется. Прерванный перенос повторяется с сохранением действующих реплик и согласованной карты.

**Изменение ключей:** новая раскладка комментариев вводится со следующего интервала; старые читаются по прежней версии. Смена числа Kafka-разделов выполняется с сохранением порядка ключа и позиции обработки; опубликованные снимки сохраняют монотонную версию. Приемник игнорирует устаревшие повторы. Число Kafka-разделов меняется отдельно, с сохранением порядка событий по ключу.

| OpenSearch | 32 primary shards по video_id, две реплики; три копии каждого шарда разнесены по M/E/N через allocation awareness | Поиск по автору, названию и тегам; обновление по версии [20] |
| Ceph | Три геокопии; EC 8+4 внутри региона | S3 multipart upload и чтение диапазонов [18] |
| Redis | Cluster в каждом регионе: минимум три primary для разных hash slots, у каждого две реплики на других хостах | Карточки, CandidatePool (60 с), FeedCache (30 мин) [17] |

На шард ClickHouse приходится около 2,39 TB полезных событий, OpenSearch — 6,32 GB документов. Это начальная оценка; их расширение не связано с tablets ScyllaDB.

Кворумы служебных компонентов и параметры локального резервирования приведены в [§10.1](#101-резервирование-компонентов). Драйверы переиспользуют ограниченное число соединений; приложение ограничивает параллелизм пакетных чтений.

**Backup:** ежедневные снимки ScyllaDB Manager за 4 недели [24]; архив Kafka/CDC с позициями — 7 дней; ежедневные backup/snapshot ClickHouse и OpenSearch — 7 дней. Видео имеет независимую копию и checksum, удаленные версии сохраняются 30 дней. Redis пересобирается.

Восстановление идет в отдельный кластер: проверка позиций, версий и квитанций, затем доступный хвост журнала. Снимки не дают общей атомарной точки всех таблиц; непокрытый журналом разрыв восстановить до последнего события нельзя. Производительность и время восстановления требуют проверки на оборудовании.

## 7. Алгоритмы

### 7.1. Персональная лента

**Задача.** По действиям пользователя выбрать подходящие ролики и выдавать их страницами по 20. Подготовка признаков и индексов выполняется вне пользовательского запроса; online используются готовые данные. Лента строится при обращении активного пользователя, а не пересчитывается по расписанию для всей аудитории.

**Подготовка данных.**

- **Интересы пользователя.** Обработчик просмотров и лайков обновляет `UserInterestProfile`: до 20 тегов с весами. Вклад просмотра — `min(1, watched_ms / (1000 × duration_s))`. Лайк добавляет такой же бонус для соответствующих просмотров из недавней истории; отметка в записи защищает от повторного начисления. Снятие лайка не отменяет исторический сигнал. Старые веса затухают по `exp(-Δt / 14 дней)`. Интересы обновляются по событиям, без повторного обхода всей истории.
- **Похожие видео — item-to-item.** Раз в сутки пакетная задача берет просмотры за 30 дней: выборку 1 % пользователей и до 20 последних уникальных видео на пользователя. Быстрые пропуски с долей просмотра меньше 0,1 исключаются. Для каждой пары считаются число совместных зрителей `c(i,j)` и число зрителей каждого видео `n(i)`. Сходство: `c(i,j) / sqrt(n(i) × n(j))`. В `ItemSimilarityByVideo` сохраняются 100 ближайших соседей каждого ролика. Пары и счетчики считаются пакетно; индивидуальные ленты всех пользователей не строятся.
- **Общие списки.** Обработчик каталога поддерживает `CandidatePool`: списки по тегам, популярности и времени публикации. Они обновляются раз в 15 с и доступны по ключам в Redis.

**Генераторы кандидатов.** При отсутствии готовой ленты Feed API читает профиль и последние 100 просмотров. Из независимых источников собирается до 1 000 кандидатов:

| Источник | Как выбираются ролики | Лимит |
| --- | --- | ---: |
| Item-to-item | Соседи трех последних видео с долей просмотра не ниже 0,1; чтение по video_id | 300 |
| По интересам | Списки пяти наиболее весомых тегов; отбор по кругу между списками | 300 |
| Популярные | Ролики из общего списка по числу просмотров | 200 |
| Новые | Ролики по времени публикации | 200 |

Дубликаты, последние просмотренные и недоступные видео удаляются. Для соседей метаданные читаются пакетом из `VideoById`, для остальных они вложены в `CandidateEntry`. Новый пользователь получает популярные и новые ролики; новое видео попадает через новизну и теги, не ожидая накопления совместных просмотров.

**Ранжирование.** L1 отбирает до 100 кандидатов по кругу из непустых источников, сохраняя их внутренний порядок: по сходству для item-to-item, весу тега для интересов, просмотрам для популярных и дате для новых. L2 — отдельный CatBoost-классификатор [27]: по сходству с просмотренными, совпадению тегов, популярности, свежести и длительности ролика оценивает содержательный просмотр относительно быстрого пропуска. Кандидаты сортируются по оценке; при равенстве — по video_id. Вес тегов здесь является пользовательским признаком, а не всем алгоритмом рекомендаций.

Модель обучается offline на выборке просмотров: просмотр не менее половины ролика — положительный пример, менее 10 % — отрицательный. Признаки сохраняются до просмотра, чтобы результат просмотра не попал во входы модели. Проверка проводится на более позднем периоде; влияние на качество ленты оценивается экспериментом. При недоступности модели используется порядок L1.

**Выдача и кэш.** До 100 ID сохраняются в `FeedCache` на 30 минут. Страницы используют общий `feed_id` и смещение. При промахе лента строится по готовому профилю и индексам, без пересчёта истории. При отказе одного источника кандидатов используются остальные, пока доступен Redis. Перед выдачей Video API проверяет ролики. Пути на случай отказа L2 и Redis описаны в [§10.3](#103-деградация-ленты-при-отказах).

```mermaid
flowchart LR
    Events["Просмотры и лайки"] --> Stream["Обновление интересов"]
    Stream --> Profile["ScyllaDB: профиль и история"]
    Events --> Batch["Offline: совместные просмотры"]
    Batch --> Neighbors["ScyllaDB: похожие видео"]
    Catalog["Каталог и счетчики"] --> Pools["Redis: теги, популярные, новые"]
    Profile --> Candidates["Генераторы кандидатов"]
    Neighbors --> Candidates
    Pools --> Candidates
    Candidates --> Filter["Объединение и фильтры"]
    Filter --> L1["L1: до 100 кандидатов"]
    L1 --> L2["L2: CatBoost"]
    L2 --> Cache["Redis: FeedCache"]
    L1 -->|"При отказе L2"| Cache
    Cache --> API["Feed API: страница из 20 видео"]
    Pools -. "Фоновое обновление" .-> Snap["Память Feed API: популярные и новые ID"]
    Snap -->|"При отказе Redis"| API
    API -->|"Проверка перед выдачей"| Video["Video API"]
```

**Выбор и нагрузка.** Item-to-item дает персональные кандидаты через короткие списки соседей; теги дополняют его там, где совместных просмотров мало. L1 ограничивает стоимость L2, а CatBoost учитывает сочетания признаков вместо одной суммы весов. Offline считаются только пары внутри ограниченной выборки, online нет перебора каталога или всей аудитории.

### 7.2. Возобновляемая публикация видео

**Блок и задача.** Pipeline принимает готовый ролик до трех минут, создает варианты 480p, 720p и 1080p и делает его видимым только после сохранения копий во всех трех регионах. Вход — завершенная multipart-загрузка, `video_id`, checksum и версия публикации. Выход — подтвержденные метаданные и девять сочетаний «качество × регион», после которых статус видео становится `PUBLISHED`.

**Последовательность.**

1. После завершения загрузки сохранить неизменный `publication_id` и три идемпотентных задания транскодирования. Повтор завершения с тем же ID возвращает текущее состояние той же публикации.
2. Для каждого качества выполнить транскодирование и сохранить объект с `object_ref`, checksum, размером и статусом. Попытки получают отдельные неизменяемые object key; актуальность результата определяется сохраненным номером попытки, чтобы опоздавшая попытка не заменила выбранный объект.
3. Проверить результат и скопировать готовые варианты в два остальных региона. `VideoProcessingState` хранит состояние каждого качества и каждой из девяти копий; ошибка или таймаут повторяет только незавершенный шаг. При недоступности региона публикация ожидает его восстановления.
4. Когда готовы все девять копий вариантов и проверены временные копии оригинала во всех трех регионах, зафиксировать READY-манифест. Затем одним conditional batch в партиции `VideoById(video_id)` сохранить переход в `PUBLISHED`, новую версию и outbox-событие для поиска и пула; доставка в Kafka выполняется через CDC. Если процесс упал между этими шагами, повтор продолжает его по сохраненному состоянию. Оригинал удаляется только после подтверждения готовности производных объектов и их копий.

**Структуры и связь с БД.** `UploadSession` и staging хранят состояние приема частей; `VideoProcessingState` — задания, версии попыток, статусы и копии; `VideoById` — пользовательскую карточку, ссылки и статус публикации. Сами файлы находятся в Ceph. Общей транзакции между ScyllaDB и Ceph нет: идемпотентные шаги и сохраненное состояние позволяют повторить незаконченные действия. До `PUBLISHED` видео не включается в поиск и `CandidatePool`.

**Альтернативы и выбор.** Синхронно транскодировать и копировать внутри запроса клиента означало бы держать соединение на время нескольких тяжелых операций, а сбой потребовал бы начать сценарий заново. Асинхронная цепочка разделяет шаги на задания и сохраняет результаты каждого; поэтому можно повторить конкретный незавершенный шаг. Публикация после готовности всех региональных копий следует принятому требованию доступности во всех регионах, хотя при сетевом сбое увеличивает время ожидания. Идемпотентность и immutable object keys предотвращают конфликт от повторных или запоздавших попыток.

## 9. Схема проекта

### 9.1. Обзор сервисов

На входе в регион LVS распределяет соединения по пулам NGINX для API, загрузки и origin. Публичные вызовы API идут по HTTPS с JSON, внутренние вызовы сервисов — по gRPC через внутренние upstream NGINX (§4.1, §8.1). Внутренний NGINX выбирает экземпляр целевого сервиса. На схемах каждый такой вызов показан одной стрелкой. Владельцы данных показаны рядом с сервисами по принципу Database per Service из лекции 9 (слайды 14, 16, 18, 20).

**Легенда.** Рамка объединяет компоненты одного сервиса. Сплошная стрелка показывает вызов, операцию с хранилищем или следующий шаг обработки. Пунктир показывает доставку событий, фоновых заданий и результатов пакетных расчётов. Если ответ API ждёт подтверждения записи в Kafka, это указано на стрелке. R — чтение, W — запись, R/W — оба действия. Стрелки к хранилищу направлены от вызывающего компонента. Фоновые компоненты помечены словом «фон». Kafka, Ceph и области данных с одинаковыми именами на разных схемах обозначают одни и те же ресурсы.

```mermaid
flowchart TB
    C["Клиент"] -->|"HTTPS / JSON"| N["LVS → NGINX API"]
    N --> A["Auth API"]
    N --> F["Feed API"]
    N --> S["Search API"]
    N --> V["Video API"]
    N --> I["Reactions API<br/>Comments API"]
    N --> E["Event API"]
    F -->|"gRPC: карточки"| V
    S -->|"gRPC: карточки"| V
    C -->|"GET видео"| CDN["CDN edge / shield"]
    CDN -->|"При промахе"| O["LVS → NGINX origin"]
    O -->|"S3 R: диапазоны"| M[("Ceph · видео")]
```

**Вход и регистрация.** Auth API проверяет учётные данные и сессии. Создание и активацию аккаунта выполняет Users API.

```mermaid
flowchart TB
    subgraph AUTH["Авторизация"]
        A["Auth API"]
        AL["Логин, сессии,<br/>проверка прав"]
        AD[("ScyllaDB<br/>LoginReservation · AuthByUser")]
        A --> AL -->|"R/W"| AD
    end
    subgraph USERS["Пользователи"]
        U["Users API"]
        UL["Создание и активация<br/>аккаунта"]
        UD[("ScyllaDB<br/>UserById")]
        U --> UL -->|"R/W"| UD
    end
    AL -->|"gRPC: создать / активировать"| U
```

Reactions API и Comments API — отдельные точки входа. Они сгруппированы на обзоре, их обработчики показаны в §9.5. Там же показаны связи с Kafka, статистикой и DWH. Для защищённых операций API запрашивает проверку сессии в Auth API. Эти однотипные вызовы описаны здесь один раз. Видео выдаётся через CDN по ссылке из карточки. Байтами управляют origin и видеохранилище, а факт просмотра сообщает клиент отдельным запросом в Event API.

При регистрации Auth резервирует нормализованный логин, вызывает Users для создания аккаунта PENDING с тем же user_id, затем активирует резерв и аккаунт. Повтор продолжает незавершённый шаг. Вход разрешён после активации обеих записей. Auth проверяет пароль по хешу из LoginReservation и выдаёт сессию. Выпуск и отзыв сессии используют LWT, проверка читает AuthByUser с QUORUM (§6.3–6.4).

| Владелец | Область данных | Как данные доступны другим сервисам |
| --- | --- | --- |
| Авторизация | ScyllaDB: LoginReservation, AuthByUser | Auth API проверяет сессии и права |
| Пользователи | ScyllaDB: UserById | Users API управляет аккаунтом |
| Видео | ScyllaDB: VideoById, VideoProcessingState. Redis: кэш карточек. Ceph: оригиналы и варианты | Video API отдаёт карточки и статус. Каталог публикует изменения. Origin читает опубликованные медиа |
| Реакции | ScyllaDB: UserVideoState | Reactions API читает собственный лайк пользователя. Изменения доставляются в Kafka через outbox и relay |
| Комментарии | ScyllaDB: CommentByVideoBucketStripe | Comments API отдаёт страницы. Изменения доставляются в Kafka через outbox и relay |
| Рекомендации | ScyllaDB: UserHistory, UserInterestProfile, ItemSimilarityByVideo. Redis: FeedCache, CandidatePool | Feed API собирает страницы |
| Статистика | ScyllaDB: VideoCounterById | Statistics API отдаёт публичные счётчики. Снимки из Kafka обновляют CandidatePool |
| Поиск | OpenSearch: производный индекс | Search API выполняет запросы |
| DWH | ClickHouse: ProductEvent | Контур выгрузки DWH готовит выборки для пакетных задач |

ScyllaDB и региональный Redis физически могут обслуживать несколько сервисов. Области таблиц и ключей имеют владельца. Только компоненты владельца обращаются к своей области напрямую. Например, поиск и лента читают карточки пакетным gRPC-вызовом Video API, а сборщик CandidatePool получает изменения каталога и счётчиков из Kafka. Relay и приёмники снимков работают в контурах соответствующих владельцев.

### 9.2. Рекомендации

**Запрос ленты.** Feed API принимает `feed_id` и смещение. При попадании в кэш он читает готовый порядок ID, при промахе собирает до 1 000 кандидатов и передаёт до 100 на ранжирование (§7.1). Ошибка обращения к Redis включает резервный путь. Все пути к выдаче страницы сходятся на проверке через Video API.

На фильтрации исключаются дубли, просмотренное и недоступное. L1 сохраняет разнообразие источников, L2 сортирует по оценке содержательного просмотра. Для нового пользователя основа выдачи — популярные и новые ролики. Резервные ветки схемы описаны в [§10.3](#103-деградация-ленты-при-отказах).

**Подготовка данных.** Профиль и история обновляются по событиям (§9.5). Сборщик пула применяет события каталога и снимки счётчиков и каждые 15 секунд публикует списки в Redis. Суточная задача item-to-item читает выборку просмотров за 30 дней и сохраняет версию индекса соседей. Обучение CatBoost использует подготовленную offline-выборку (§7.1). Feed API использует готовую модель.

```

CandidatePool применяет версии карточек и счётчиков. Если локальное состояние сборщика утрачено, он восстанавливает его из каталога через Video API и сохранённых итогов через Statistics API, затем применяет хвост событий. Чтение для восстановления идёт в отдельном фоновом бюджете. Новый выпуск соседей становится доступен после завершения записи. Незаконченный расчёт оставляет активным прежний выпуск.

        U -->|"S3 W: части"| M

    API --> A
    UP --> U
    REL -. "Задания транскодирования" .-> K["Kafka"]
```

Подтверждение завершения загрузки означает, что оригинал принят и publication_id с заданиями сохранён. Для трёх качеств сохраняются устойчивые ID заданий. Relay читает исходящие записи, а Kafka переносит задания и ссылки на объекты.

**Фоновая обработка.** Worker по заданию читает оригинал, кодирует своё качество и записывает неизменяемый объект попытки. Состояние задания определяет, какой результат принят. Проверка копий фиксирует checksum и готовность по каждому качеству и региону. Из сохранённого прогресса обработка продолжает только незаконченные шаги.

```mermaid
flowchart TB
    KI["Kafka · задания"] -. "publication_id, качество" .-> W
    subgraph VIDEO["Видео · фон"]
        W["FFmpeg worker"]
        G["Проверка checksum<br/>и геокопий"]
        P["Публикация READY → PUBLISHED"]
        PS[("ScyllaDB<br/>VideoProcessingState")]
        M[("Ceph · staging и варианты")]
        VC[("ScyllaDB · VideoById")]
        REL["Relay каталога"]
        W -->|"S3 R/W: оригинал и вариант"| M
        W -->|"R/W: попытка и результат"| PS
        W -->|"Результат сохранён"| G
        G -->|"S3 R/W: копии и проверка"| M
        G -->|"R/W: копии и READY"| PS
        G -->|"Манифест READY"| P
        P -->|"W: карточка, версия и outbox"| VC
        REL -->|"R: outbox / CDC"| VC
    end
    REL -. "Изменение каталога" .-> KO["Kafka · каталог"]
```

READY фиксируется после проверки девяти сочетаний «качество × регион» и временных копий оригинала в трёх регионах. Затем одна условная запись в партиции VideoById меняет статус на PUBLISHED и сохраняет версию и outbox (§7.2). При сбое после READY публикация продолжится по сохранённому манифесту. При повторе задания актуальный номер попытки защищает от запоздавшего worker. Оригинал очищается после подтверждения готовности вариантов и копий. Индексатор и сборщик CandidatePool получают событие после фиксации PUBLISHED.

### 10.1. Резервирование компонентов

Расчётный сценарий — отказ одного ЦОДа. Трафик уходит в два оставшихся (ДЗ 3.3), а пулы NGINX выдерживают потерю ещё одного узла на пул (ДЗ 4.3). Запас приложений и хранилищ проверяем на стенде.

| Компонент | Резерв и обнаружение отказа | Что происходит |
| --- | --- | --- |

| ScyllaDB | По реплике в каждом ЦОДе, QUORUM 2/3. Для LWT — SERIAL + QUORUM | Два ЦОДа продолжают работу. При таймауте результат записи проверяется по ID операции |
| Kafka, Streams и приёмники снимков | RF=3, `acks=all`, минимум 2 реплики в ISR. Резерв Streams в другом ЦОДе, состояние в changelog | Kafka выбирает лидера из ISR. При ISR <2 подтверждения записи нет. Streams восстанавливает состояние из changelog [15], [26], [42] |
| Relay, сверка и фоновые задачи | Резервные исполнители, сохранённые позиции или шаги. Сигналы — отставание, возраст задания и ошибки | Новый исполнитель продолжает с сохранённой позиции. Для рекомендаций сохраняется предыдущая полная версия индекса и модели |

| KRaft, Keeper и OpenSearch cluster-manager | У каждой системы по три голосующих узла, по одному в ЦОДе | При отказе одного узла остаётся большинство 2/3. Кворум проверяем отдельно от числа копий данных [28], [29], [31] |

| Телеметрия | По два Prometheus на регион, три Alertmanager, несколько Collector и отдельный ClickHouse | При сбое приёмника события ждут в ограниченной очереди. Переполнение снижает полноту диагностики, API продолжает работать |
| Инфраструктура и резервные копии | Дубли питания и сети, региональные копии конфигураций, зашифрованные копии ключей. Резервные копии данных хранятся отдельно. Проверяем срок TLS и свежесть копий | При сбое CI/CD работает текущая версия. После порчи данных поднимаем отдельный кластер из копии и доступного журнала (ДЗ 6.6) |


### 10.2. Асинхронные потоки

| Паттерн и поток | Что подтверждаем и как повторяем |
| --- | --- |
| **Transactional outbox** · лайки, комментарии, каталог и задания видео | Лайк и комментарий подтверждаются после LWT, которая сохраняет изменение и outbox в одной партиции. Relay отмечает доставку после ack Kafka. Запись в ScyllaDB и отправка в Kafka подтверждаются отдельно. Если ack был, а отметку записать не успели, повтор уйдёт с тем же `event_id`. После истечения окна CDC задача повторно отправляет неподтверждённые записи из outbox. Повтор команды с тем же `operation_id` в окне идемпотентности возвращает прежний результат [15], [19] |
| **Сбор событий** · просмотр → Event API → Kafka | API отвечает после `acks=all`. Клиент при повторе сохраняет `event_id`. Streams отбрасывает дубли в пределах окна повтора |
| **Цепочка фоновых заданий** · загрузка → FFmpeg → геокопии → публикация | Приём оригинала подтверждаем после проверки файла и записи задания. Worker продолжает сохранённый шаг, а номер попытки защищает от опоздавшего результата. `PUBLISHED` ставится после проверки всех копий (ДЗ 7.2) |
| **Асинхронные модели чтения** · Kafka Streams → история, профиль и счётчики | Streams фиксирует позицию, состояние и выходные события одной транзакцией Kafka. Приёмник фиксирует позицию после записи более нового снимка в ScyllaDB или проверки его версии. Повтор абсолютного значения счётчика не даёт второго начисления [26] |
| **Событийное обновление поиска** · каталог → OpenSearch | Индексатор проверяет каждый ответ Bulk и сохраняет позицию, когда обновление прошло или в индексе уже есть более новая версия. Повтор версии безопасен, если она содержит то же полное состояние [41] |
| **Фоновые обновления** · CandidatePool, DWH и модели | Сборщик обновляет списки по версиям каталога и счётчиков. После сбоя начинает со снимка и догоняет журнал. Загрузчик DWH фиксирует позицию после записи пачки, выборка с `FINAL` убирает дубли по дате и ID. Новую модель включаем после готовности всего выпуска (ДЗ 9.2, ДЗ 9.5) |

**Сверка поиска.** Фоновый процесс сравнивает версии каталога и индекса и отправляет исправления через Kafka. Цель — суточный обход с лимитом 5 000 карточек/с. При нагрузке на каталог или поиск сверка замедляется и продолжает с сохранённой позиции. При удалении версия сохраняется в записи `deleted=true` минимум 30 дней, чтобы позднее событие не вернуло ролик в поиск. Старые повторы за пределами рабочего окна обрабатываются отдельно от текущих счётчиков и индекса.

### 10.3. Деградация ленты при отказах

**1. CatBoost не отвечает.** L2 работает в отдельном пуле. При ошибке, перегрузке или таймауте в 50 мс Feed API сохраняет порядок L1 в FeedCache. После серии ошибок L2 вызывается только для проверки восстановления. Пользователь получает ленту с более простым ранжированием. После восстановления CatBoost участвует в создании новых лент, порядок уже сохранённых страниц держится до истечения кэша.

```mermaid
flowchart LR
    L1["Порядок L1"] --> L2["CatBoost · до 50 мс"]
    L2 -->|Успех| C["Сохранить порядок в FeedCache"]
    L1 -->|"Ошибка или таймаут L2"| C
    C --> V["Video API · проверить ролики"]
```

**2. Redis недоступен.** Сборщик CandidatePool публикует популярные и новые ID одним списком с версией. Feed API раз в 15 с читает этот список вне пользовательского запроса и целиком заменяет локальный снимок. При ошибке чтения оставляет последний полный снимок, в котором до 1 000 ID. Если Redis недоступен, экземпляр отдаёт общую ленту из последнего снимка возрастом до 15 минут. При обычном промахе кэша персональная лента строится штатно.

```mermaid
flowchart LR
    R["CandidatePool в Redis"] -. "Обновление раз в 15 с" .-> S["Снимок в памяти Feed API"]
    A["Ошибка Redis"] --> S
    S -->|"Снимок не старше 15 мин"| V["Video API · проверить ролики"]
    V -->|"Проверка прошла"| P["Общая лента · до 20 роликов"]
    S -->|"Снимка нет или он просрочен"| E["503"]
    V -->|"Проверка недоступна"| E
```

В обоих режимах Video API проверяет публикацию, удаление и права показа. Для резервной страницы Feed API отправляет один пакет до 40 ID, без повторов, с отдельным лимитом параллелизма. У общей ленты свой `feed_id` и смещение в снимке. При смене версии или возврате Redis выдача начинается заново. Кэш прогревается постепенно. При расчётном пике на регион приходится до 7 503 пакетных вызовов/с. Запас Video API проверяем вместе с остальным трафиком. Если лимит параллелизма исчерпан, Feed API отвечает 503.

### 10.4. Цели и проверка восстановления

За 30 дней цель для ленты, лайков и комментариев — 99,9% успешных ответов за 3 с. Для ленты целевой p95 — 500 мс. Для публикаций — 99% за 10 мин после приёма оригинала, для обновления счётчиков — 99% событий за 60 с. Долю страниц из L1 и локального снимка измеряем отдельно.

| Отказ | Что сохраняется | Цель восстановления |
| --- | --- | --- |
| Один ЦОД | Подтверждённые записи ScyllaDB и Kafka при исправных оставшихся копиях (RPO 0) | API ≤60с для 99% контрольных запросов, Kafka/Streams ≤5 мин |
| Один LVS, NGINX или API | Подтверждённые записи хранятся вне процесса | Переключение ≤30с |

| Потеря Redis | Исходные данные остаются в хранилищах | Лента переключается на годный снимок. Полный прогрев кэша замеряем |
| Потеря индекса | Каталог сохраняется | Поиск восстанавливается из каталога. Время перестройки замеряем |
| Порча данных | Проверенная резервная копия и доступный журнал | Срок определяется пробным восстановлением |
